# Thurmaston village website

Static HTML/CSS/JS site (no build step) for the "Memories of Thurmaston" community site. See `PHOTOS.md` and `HOW-TO-ADD-PHOTOS.md` for the Google Drive → GitHub photo sync pipeline.

## Site structure

Five pages: `index.html` (homepage — hero banner, short intro, photo archive tiles, full historic map with all categories, shared memories, share-a-memory form), `category.html` (one template driven by `?cat=streets|people|events|nature|other`, showing the map and photo grid locked to a single category — linked from the homepage's photo archive tiles), `place.html` (one template, driven primarily by `?photo=ID` — a dedicated page for *every* photo, not just ones with a hand-written story; `?slug=X` is optional/derived, see "Story pages" below), `contact.html`, and `admin/index.html` (the Decap CMS login/editor). There used to be a separate `memories.html`; it was merged into `index.html` so the site lands directly on that content instead of a separate homepage. Don't recreate a `memories.html` — anything that used to link there should point at `index.html` (with `#photos`, `#map`, or `#share` anchors as needed).

There is no photo lightbox/modal on `index.html`/`category.html` any more — clicking any photo thumbnail (grid, map popup) navigates straight to `place.html?photo=ID`, a real page. The only remaining modal on the site is the small "Know more about this photo?" popup on `place.html` itself (`.place-know-more-modal`, opened by `#place-know-more-btn`) — don't reintroduce a full-photo lightbox; that pattern was deliberately replaced because it was confusing for a non-technical user testing the site.

`js/photos.js` and `js/map.js` are shared by all pages that use them. A page sets `window.LOCKED_CATEGORY = "streets"` (etc.) in an inline `<script>` before loading `photos.js`/`map.js` to lock both to one category; `index.html` doesn't set it, so it shows everything. Don't fork these scripts per-page — extend the shared ones.

## Categorisation rule — always read from the Drive folder structure

A photo's category (`streets`, `people`, `events`, `nature`, `other`) is decided **only** by which Drive subfolder it was uploaded into — that's what `CATEGORY_FOLDERS` in `automation/drive-photo-sync.gs.js` encodes, and it's already correct in `data/photos.json`.

**Never recategorise based on what's visually in the photo.** The folder is the only signal that counts, in both directions:
- A photo uploaded to "Streets & Buildings" stays `streets` even if a person appears in it.
- A photo uploaded to "People" stays `people` even if a building is visible behind them, and a photo uploaded to "Events" stays `events` even if it's mostly one person's portrait — the split between the two is itself a judgement call made once, at upload time, by whoever's filing it; it isn't something this codebase should try to re-derive later from a caption or a photo's contents.

`people`/`events` started as one Drive folder ("People & Events") and got split into two ("People" and "Events") — `CATEGORY_FOLDERS` still maps the old folder name too, so nothing breaks if that Drive folder hasn't actually been renamed/split yet. Existing photos already categorised `people` were **not** retroactively reclassified into `events` when this split happened — that would mean guessing at photo content, which is exactly the thing this rule exists to prevent. They can be moved by hand later (Category dropdown, Photos collection in the admin) by someone who can actually see what's in them.

When adding or editing anything that assigns a category by hand (e.g. `data/map-pins.json` entries for the Historic Map), copy the category straight from that photo's existing entry in `data/photos.json` rather than guessing from the subject matter.

## General rule: a photo's Drive folder decides how it's used, full stop

This applies beyond just category. Whatever folder a photo is uploaded into determines its role according to that folder's defined behaviour in `automation/drive-photo-sync.gs.js` — never assume a photo can serve double duty across folder purposes just because the same underlying file happens to sit in two folders.

Concretely: **Hero images** photos are for the homepage banner (`data/hero.json`) only. Even when the exact same Drive file is also uploaded to a category folder (so it's also in `data/photos.json`), it must not show up in the photo archive, its category tiles, or site search — `js/photos.js`'s `PHOTOS_DATA_PROMISE` filters archive photos against `data/hero.json` by filename (not full path, since the two pipelines resize the same file into different folders — `images/photos/` vs `images/hero-photos/` — under an identical filename) to enforce this. If a new dedicated folder is ever added to the sync script, give it the same treatment: figure out what "belongs only to that folder's purpose" means, and exclude it from other surfaces rather than letting it leak across by default.

## Caption cleanup — filename becomes caption, minus Dad's filing codes

Dad's Drive filenames often carry his own archival codes — a leading catalog number ("003 ...") and/or a "MOT 1-11" style reference. `cleanCaption()` in `automation/drive-photo-sync.gs.js` strips both of those (and only those) before the filename becomes a photo's public caption, e.g. "003 Generous Briton c1936 MOT1-11.jpg" → caption "Generous Briton c1936". Don't strip anything else speculatively (parenthetical notes, credit-looking words, etc.) — those are still part of his description and might be meaningful.

The untouched original filename is never discarded: it's stored verbatim in that photo's `ref` field in `data/photos.json` and shown as a small "Ref: …" tag on the photo's own page (`.place-photo-panel-ref` in `js/place.js`), and it's included in the photo search haystack too, so searching his catalog number or MOT code still finds the photo.

## Map pins come from two sources — don't require a manual step for either

`data/map-pins.json` (`{ "pins": [...] }`) is a small hand-curated list, editable via the admin (richer written descriptions, for pins worth a proper story). But most located photos get their `lat`/`lng` automatically, via an "@lat,lng" in the filename or a recognised place subfolder (see `KNOWN_PLACES` in `automation/drive-photo-sync.gs.js`) — those must **not** require someone to also hand-add a curated pin, or pins silently go missing (this happened once: 5 photos had coordinates, only 2 showed on the map, because 3 were never added to the curated list).

`js/map.js` fixes this by fetching `data/map-pins.json` and merging it with an auto-generated pin for every other photo in `data/photos.json` that has `lat`/`lng` and isn't already covered by a curated entry (matched by `photoId`). Keep it this way — if you ever touch map pin logic, a located photo appearing on the map should never depend on a manual `data/map-pins.json` edit.

Curated pins store their location as one `coords` string field (e.g. `"52.679363, -1.097994"`) rather than separate `lat`/`lng` numbers — deliberately, to match the copy-paste-from-Google-Maps workflow (right-click a spot, click the coordinates that pop up to copy). `parseCoords()` in `js/map.js` splits it back into `lat`/`lng` at load time. Photos use the same `coords` string convention in their own per-file storage (see "Photos: one file per photo" below) — but `data/photos.json`, the generated aggregate, still gets plain numeric `lat`/`lng` per photo, unchanged from before; `scripts/rebuild-photos-index.js` does that `coords` → `lat`/`lng` conversion at build time, so `js/photos.js`/`js/map.js` never had to change.

`js/map-categories.js` holds only `MAP_CATEGORIES` (the fixed colour/label taxonomy) — that one's a genuinely static lookup table, not editorial content, so it stays as plain JS rather than a CMS-editable file.

## Photos: one file per photo, plus a generated aggregate

`data/photos/<id>.json` (one file per photo, e.g. `data/photos/1RjrLTG9-003-generous-briton-c1936-mot-1-11.json`) is the real, CMS-editable source of truth — analogous to `data/pages/<slug>.json`. `data/photos.json` is a **generated aggregate**: a plain bare array, in exactly the shape it's always been, which is the single file every front-end script (`js/photos.js`, `js/map.js`, `js/place.js`) and the admin previews actually fetch. Never hand-edit `data/photos.json` directly — it gets overwritten.

`.github/workflows/rebuild-photos-index.yml` + `scripts/rebuild-photos-index.js` regenerate `data/photos.json` automatically on every push that touches `data/photos/**` (a Drive sync or a CMS save), sorting newest-first by each photo's `addedAt` ISO timestamp, and commits the result straight back to `main`. `automation/drive-photo-sync.gs.js`'s `appendMetadataEntry` (new photo) writes directly to a single `data/photos/<id>.json` file rather than reading/writing the whole array — cheaper, and it's what makes the file safely CMS-editable without a giant merge-conflict-prone list.

This split exists for the same reason `PREVIEW_COUNT` caps the homepage archive grid: the admin has to stay usable at hundreds/thousands of photos, so photos get their own Decap **folder collection** (`photos` in `admin/config.yml`, one entry per file, picked by caption) rather than a single big `list` widget like `map-pins.json`'s (fine there, since that list stays small and hand-curated).

**Decap folder/file collections silently drop any field not listed in `config.yml`'s `fields:` on save.** The `photos` collection therefore lists every field that exists on a photo — including ones that shouldn't normally be hand-edited (`id`, `ref`, `addedAt`) — labelled "Internal" with a hint rather than truly locked (Decap has no fully reliable read-only widget), the same operator-discipline posture already used for Map Pins' "Internal ID" field. If you ever add a new field to the photo schema, add it to this collection too, or it'll vanish the next time that photo is saved through the CMS.

**Adding a photo straight through the admin** — `create: true` on the `photos` collection, with `src` as an `image` widget (upload lands in `images/photos/`, same folder Drive-synced photos use) so "upload the file, then fill in the details" works in one form. Three fields are deliberately left for the human to skip rather than compute, and `scripts/rebuild-photos-index.js` fills them in at build time instead of asking someone to hand-type them (and, since it edits the per-file JSON directly when it does, the fix sticks — it isn't redone from scratch on every rebuild):
- `id` — always overwritten with the entry's own filename (`file.slice(0, -".json".length)`), never trusted from the file. New entries get a unique filename for free from the collection's `slug:` template (`{{year}}{{month}}{{day}}{{hour}}{{minute}}{{second}}-{{slug}}`), so nobody has to invent an ID by hand.
- `ref` — if left blank, defaults to the uploaded image's own filename (`decodeURIComponent(path.basename(photo.src))`). Drive-synced photos already set a richer `ref` (Dad's original, uncleaned filename) themselves, so this fallback only ever fires for a photo added through the CMS.
- `addedAt` — if left blank, backfilled with the current time **and written back to that photo's own file**, not just the generated aggregate, so it's set once and stays stable (a naive "default to now" only in the aggregate would make that photo look newer on every unrelated rebuild, since "now" keeps moving). This is also why `.github/workflows/rebuild-photos-index.yml` stages `data/photos/` as well as `data/photos.json` in its commit step.

## Every photo gets its own page — `place.html?photo=ID`

Every photo in the archive has a real, dedicated page — not just ones with a hand-written story. Clicking any photo thumbnail (grid, map popup) navigates to `place.html?photo=<id>`. There is no modal/lightbox for viewing a photo any more; this was a deliberate architecture change (the old click-to-open-a-modal pattern was confusing for non-technical users) — don't reintroduce one.

`js/place.js` treats `?photo=ID` as primary and `?slug=X` as optional/derived:
- If only `?photo=ID` is given, it looks up that photo, and — if that photo's own `pageSlug` field is set — also fetches that page's `data/pages/<slug>.json` for its extra written content. If `pageSlug` isn't set, the page still renders fine with just the photo's own facts (no page, no blocks).
- `?slug=X` can also be passed explicitly (e.g. from an old link, or a pin with a `pageSlug` but no specific photo in mind) — in that case the page falls back to rendering just the page content, without a photo panel, if there's no `?photo=` too.
- A photo with no `pageSlug` at all still gets a perfectly good page: photo, facts, History (if set), and the "Know more" button — it just has no extra blocks/written-story section beneath.

**`data/pages/<slug>.json`** (a *Story page* — optional extra content, not required for a photo to have a page) — one file per page: `{ "title": "...", "blocks": [...] }`. Each block has a `type` of `text` or `photo`:
  - `text`: `{ "type": "text", "text": "..." }` — rendered by `js/place.js`'s tiny built-in markdown-lite (paragraphs on blank lines, `**bold**`, `*italic*`, `[label](url)` links). Not a full markdown library on purpose — this is a static, no-build-step site, so no npm dependency was added for it. Don't casually extend the syntax without checking `renderInline`/`renderTextBlock` in `js/place.js` can actually handle it.
  - `photo`: `{ "type": "photo", "photoId": "..." }` — must match an id in `data/photos.json`; renders as a thumbnail linking to that photo's own page (`place.html?photo=ID`). In the admin, `photoId` is a `relation` widget against the `photos` collection (search by caption) rather than a plain text box needing a hand-typed id — the same pattern `pageSlug` already uses to reference `pages`. Don't revert this to a plain `string` — a photo's `id` is never shown anywhere on the live site (only `ref` is, as the "Ref:" tag), so there'd be no way to find the right value to type in by hand.
- A photo's `pageSlug` field (the filename of the Story page, minus `.json`) is what opts it into showing a Story page's extra content — but there's deliberately **no field for it in the Photos admin collection any more** (removed at the user's request: every photo already gets its own full page automatically, so a per-photo "attach a story page" step just added confusion for no real benefit for a family archive with one non-technical uploader). A handful of photos from before that change still have `pageSlug` set in their own `data/photos/<id>.json` and keep working exactly as described above — don't strip it from them. Going forward, the supported way to give a *place* extra written content is a Map pin's own "Full story page" field (see `map_pins` below), not a per-photo link.
- On `place.html`, the page is built up in this order, each piece skipped silently if there's no photo (bare `?slug=X`) or the relevant field is empty:
  - A **facts panel** (`.place-photo-panel`) at the top — caption, date/location, category/credit, ref, and (if the photo has coordinates) a "View on map →" link that jumps to `index.html?photo=ID#map`, which `js/map.js` picks up via its own `?photo=` param on load to fly to and highlight that pin.
  - **History** (`.place-history`) gets its own full-width, light-background section directly under the facts panel, not folded into it — a light background reads better for a longer paragraph than the panel's narrow dark info column did, which is also why it's not just left inside `.place-photo-panel-info` alongside the terser caption/date/credit/ref facts.
  - A **"Know more about this photo?" button** (`#place-know-more-btn`) — opens the submit form in a small popup (`.place-know-more-modal`) rather than showing it inline on the page; see "Know more" below.
  - The Story page's own `blocks` (the extra written content, if a Story page is linked) — labelled just "Content" in the admin, since the facts above already cover caption/date/location/etc., this is only for anything beyond that.
  - A **"← Back to `<Category>`"** link (`#place-back-link`, in the page-hero) pointing at `category.html?cat=X` — lets a reader get back to the archive they came from.
  - A **"More photos from `<location>`"** grid (`.place-related`) listing every other photo whose `location` field is an exact match (trimmed, case-insensitive) to this one's. Depends entirely on photos being archived with the *same* location text, not just similar — that's on the person filling in Location in the admin, not something the code can infer.
- **Ordinary photos** get their `location` and `history` set through the admin's **Photos** collection (see "Photos: one file per photo" below) — pick the photo by caption, fill in the field, save. A photo can alternatively get a proper entry in `data/map-pins.json` (reusing its existing `photoSrc`/`photoId` and re-pasting its coordinates as a `coords` string), which gets it a name, a description, and its own `pageSlug` editable through the Map Pins admin form, and automatically suppresses the auto-generated version of that same pin (matched by `photoId`). That's still the answer for a photo that didn't get coordinates at upload time — add/fix them there rather than needing to re-upload.

There used to be a PDF-attachment feature (a `doc` field on photos, a `document` block type on Story pages, a "View document" button) — it was removed entirely at the user's request, since it added a step that confused a non-technical editor. Don't reintroduce it; PDFs already in `documents/` were left in the repo untouched, just unlinked.

## "Know more about this photo?" — a small popup, not an inline section

Clicking `#place-know-more-btn` on a photo's page opens `.place-know-more-modal`, a small centred popup (`js/place.js`'s `renderKnowMore`) — not an inline form on the page. This was a deliberate simplification (the button-then-popup pattern reads more clearly than a form always sitting on the page) — don't turn it back into an always-visible inline section.

The form itself (`renderSubmitForm` in `js/place.js`) follows the exact same pattern as the homepage's existing "Share your memory"/"Know a building" forms: static, `action="#"`, with the same "not connected to a mailbox yet" note. Not wired up on purpose, matching those — wire all of them up together later via Netlify Forms/Formspree, not just this one. Its CSS still lives under the `.photo-lightbox-submit` class name (`css/style.css`) — kept from when this form grew up as part of the old lightbox, since every field id/label already refers to it that way; only the outer chrome (now `.place-know-more-modal`/`.place-know-more-inner`) changed. `place.html`'s modal body carries both classes (`class="place-know-more-body photo-lightbox-submit"`) so that styling still applies — if you ever rename one, rename the other in step.

The form's first field, "About this photo" (`name="photo-ref"`), is a real (not hidden) `readonly` input pre-filled with the photo's `ref` — same `photo.ref || photo.caption || photo.id` fallback chain used elsewhere for "something readable to show." Deliberately a genuine named form field, not just a `<p>` — the hidden `photo-id` field alone isn't something a human reads in a notification email once this gets wired up, so this exists purely so whoever receives that email can tell which photo it's about at a glance, without cross-referencing an internal id.

## Display convention: thumbnail/map-sized vs the full photo page

Deliberate split, requested explicitly — don't blur it when adding fields:

- **Thumbnail/map-sized displays** (photo grid thumbnails, the map sidebar list, map popups) show only **Name, Date, Location** — compact, one or two lines. Grid thumbnails show this as a glass gradient-overlay caption (`.photo-thumb-caption` in `js/photos.js`/`css/style.css`, same visual language as the hero banner and category tiles); the map list/popups combine period+location into one subtitle line (`[item.period, item.location].filter(Boolean).join(" · ")`, in `js/map.js`).
- **The photo's own page** (`place.html?photo=ID`) is the one place that shows everything: Name, Date · Location, Category · Credit, written **History** (`.place-history`, only shown when `photo.history` is set), Ref, a "View on map" link if located, the "Know more about this photo?" button, and (if linked) the Story page's extra content and related photos.

Two optional fields on **both** photo entries and `data/map-pins.json` pins:
- `location` — free text, e.g. `"Garden Street"`. Not the same as `category` (Streets & Buildings etc.) — this is an actual place name, filled in by hand as it becomes known. Curated pins set it via the Map Pins admin form; ordinary photos via the Photos admin collection.
- `history` — **photos only** (curated pins already have `description` serving the same role for their popup). A longer written paragraph, shown on the photo's page beneath the facts panel. Optional — most photos won't have one yet.

**Admin: `admin/index.html` + `admin/config.yml`** is [Decap CMS](https://decapcms.org/), backed by `git-gateway` (Netlify Identity for login, saves commit straight to `main` on GitHub, no custom backend code). Three collections, `photos` listed first — Decap opens the first-listed collection by default on login, and Photos is the one used day to day — then `pages` (the story-page blocks editor described above), then `map_pins` (edits `data/map-pins.json`, including a `relation` field to pick a `pages` entry for `pageSlug`). `publish_mode: simple` — no draft/review step, matching the rest of the site's single-trusted-uploader approach; switch to `editorial_workflow` in `config.yml` if that ever needs to change (e.g. more admins added).

`admin/index.html` also registers a **custom live preview** for all three collections (`CMS.registerPreviewTemplate`), styled with the site's real `css/style.css` (`CMS.registerPreviewStyle`) so the preview pane actually looks like the live page, updating as you type. The `photos` preview mirrors the real photo page markup (`.place-photo-panel*`/`.place-history` classes from `place.html`/`js/place.js`). The `pages` preview's text-block rendering (`renderTextBlockPreview`/`renderInlinePreview`) is a hand-kept-in-sync duplicate of `js/place.js`'s `renderTextBlock`/`renderInline` — it has to be a duplicate because it runs inside the CMS's preview iframe, a separate JS context that can't import that file. If you change the markdown-lite syntax in one, change it in the other.

`PagePreview` fetches `/data/photos.json` **once**, in `componentDidMount`, to resolve `photo` blocks — always with `{ cache: "no-store" }`. Without that, a browser-cached response from an earlier page load can stick around as "Photo not found" for a photo that was actually added later in the same session, even though the real saved data and the published site are both fine (this happened once — the fetch wasn't cache-busted yet). If you add another one-time external fetch anywhere in the admin, cache-bust it the same way.

**Two-way linking gotcha (historical, mostly moot now)**: a photo's `pageSlug` and a story page's existence used to be two independent things set by hand in two different collections — nothing kept them in sync automatically, and creating a story page with a `photo` block pointing at photo X did **not** set photo X's own `pageSlug` back (this happened for real, for the Ian Lavendar photo/page). Now that the Photos collection no longer has a `pageSlug` field at all (see "Every photo gets its own page" above), this mismatch can't be created through the admin any more — the only place `pageSlug` is still set by hand is a Map pin's own "Full story page" field in `map_pins`, which is self-contained (no second field elsewhere to forget).

**"Muted" fields, for the Photos form specifically** — most of that collection's fields are things that are already correct from the Drive sync or rarely need changing (Caption, Date, Credit, Coordinates, Location, History, Consent, and the three Internal fields); Category is the one field that always needs an active decision on every photo. To make that visually obvious rather than presenting a form full of equally-weighted boxes, those "usually fine as-is" fields use custom `muted-string`/`muted-text`/`muted-boolean` widgets (`CMS.registerWidget` in `admin/index.html`) — plain inputs with dimmed grey styling, still fully editable, just visually receded. **Deliberately not applied to the Photo (`src`) field** — that's Decap's real `image` upload widget, and reimplementing that upload machinery just to grey it out risks breaking the actual upload path (see the media_folder leading-slash bug this project already hit once) for a cosmetic win; its hint does the "leave this alone" work instead. `pattern:` validation (e.g. Coordinates' "lat, lng" format check) still applies to a `muted-string` field exactly as it would to a plain `string` one — Decap validates by field config centrally, not per-widget.

**Search and grouping in the Photos collection** — a search box is automatic on any Decap folder collection, no config needed. `view_filters` (one quick-filter button per category) and `view_groups` (cluster the list by category) are also set on the `photos` collection so the list stays browsable once it's a few hundred photos deep, not just searchable by caption text.

**Edit log** — every CMS save is a git commit (that's how `git-gateway` works), so there's no separate history to maintain: `admin/index.html` adds an "Edit log" page to Decap's own sidebar (`CMS.registerAdditionalLink`) that fetches recent commits straight from GitHub's public commits API and lists message/author/date. Only reachable from inside the logged-in admin, never linked from or shown on the public site. Deliberately unfiltered (shows Drive photo syncs too, not just CMS edits) — that's more useful as a single "what changed on the site" view than a narrower one. `registerAdditionalLink` is a newer, less-documented part of Decap's API, so it's feature-checked (`typeof CMS.registerAdditionalLink === "function"`) before use — if it's missing in whatever CMS version loads, the rest of the admin still works, it just won't have this page.

This can't be tested end-to-end without the one-time Netlify Identity setup in the site owner's Netlify account (enable Identity, invite a user) — I can build and verify the config's shape and the front-end rendering, but not the actual login flow, myself.

## Backup: GitHub → Drive, one-way, editorial data only

`backupToDrive()` in `automation/drive-photo-sync.gs.js` is a separate function (own daily trigger, not part of `syncPhotos`) that reads the live `data/photos.json`, `data/map-pins.json`, and every `data/pages/*.json` from GitHub and writes them into a Google Sheet ("Memories of Thurmaston — site backup") inside the same Drive folder, overwriting it each run. Requested explicitly as *just* a safety net, not a working copy — don't build anything that reads from or writes back into that sheet; it's one-way, GitHub is still the single source of truth. The photos themselves don't need backing up (they started in Drive); this exists because the editorial layer on top — cleaned captions, `location`, `history`, map pin descriptions, story page text — only lives on GitHub otherwise.
