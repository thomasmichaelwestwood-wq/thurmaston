# Thurmaston village website

Static HTML/CSS/JS site (no build step) for the "Memories of Thurmaston" community site. See `PHOTOS.md` and `HOW-TO-ADD-PHOTOS.md` for the Google Drive → GitHub photo sync pipeline.

## Site structure

Thirteen pages: `index.html` (homepage — a full-bleed hero with the search box and a Village Chronology teaser card, category tiles, shared memories, share-a-memory form — see "Homepage: photo-archive-first" below), `category.html` (one template driven by `?cat=streets|people|events|nature|aerial|other`, showing the map and photo grid locked to a single category — linked from the homepage's category tiles, except Events which links to `events.html` instead, see "Events" below), `map.html` (the full interactive map — all categories, sidebar list, filters, the "know a building" submission form — linked from the homepage's map card, the footer, and search; not embedded on the homepage itself any more), `place.html` (one template, driven primarily by `?photo=ID` — a dedicated page for *every* photo, not just ones with a hand-written story; `?slug=X` is optional/derived, see "Story pages" below), `location.html` (one template driven by `?loc=<key>` — a chronological timeline of every photo sharing one exact place, reachable via a banner on any of those photos' own `place.html` pages — see "Location timeline"/`placeKey` below), `events.html` (list of Event Pages, reached from the homepage's Events tile) and `event.html` (one template driven by `?event=<id>` — one Event Page's own description and photo gallery — see "Events" below), `chronology.html` (the village's year-by-year timeline — see "Village Chronology" below), `year.html` (one template driven by `?year=X` — everything from one year: chronology entries, events and photos, each with a checkbox and a pick-your-own PDF export — see "Year pages" below), `cemetery.html` (a searchable directory of headstones) and `grave.html` (one template driven by `?grave=<id>` — a headstone's number, dates and what3words location — see "Cemetery" below), `contact.html`, and `admin/index.html` (the CMS login/editor). There used to be a separate `memories.html`; it was merged into `index.html` so the site lands directly on that content instead of a separate homepage. Don't recreate a `memories.html` — anything that used to link there should point at `index.html` (with `#photos` or `#share` anchors as needed).

## Homepage: photo-archive-first, map de-emphasised

Requested explicitly — the site is "Memories of Thurmaston," but the homepage used to give the interactive map roughly equal billing with the photo archive (a full-height embedded map, its own sidebar/filter/submission-form, directly on the front page), which read as two competing attractions rather than a photo archive with a map as a secondary feature. Also requested: the hero banner was too tall.

- **`.hero`** (`css/style.css`) first just shrunk from `height: 62vh; min-height: 380px; max-height: 620px` to `height: 38vh; min-height: 260px; max-height: 420px`. Later split into a side-by-side layout on request — `.hero-content` (text, on a solid `var(--green-900)` background, the same brand-dark green the header/footer already use) and `.hero-media` (the photo, `.hero-slide` unchanged inside it) sitting next to it. This replaced the old full-bleed-photo-with-text-overlay-and-gradient design — text is no longer laid over the photo at all, so the old `.hero-slide::after` dark gradient overlay (needed for text legibility on top of a photo) was removed, it has no job any more. `js/main.js`'s hero-photo-loading logic (`hero.querySelector(".hero-slide")`) didn't need to change — `.hero-slide` still exists, just now nested inside `.hero-media` instead of being a direct child of `.hero`.
- **`.hero-content`'s contents grew over several passes into: `<h1>`, `.hero-subtitle`, `.hero-lede` (the longer "A community archive of old photographs…" paragraph — moved in from a separate `.tiles-lede` block that used to sit between the hero and the search box), `.hero-search` (see below), then `.hero-cta`** — now just the one "See the interactive map" button; a "Browse the photo archive" button used to sit alongside it but was removed once the archive was reachable straight from the hero's own search box, making a dedicated button to it redundant in the same breath. Order matters here for both visual hierarchy and `justify-content: center`'s vertical centering — don't reorder without checking the hero doesn't overflow at `min-height: 300px` (see mobile note below).
- **`.hero-media` is sized to the hero photo's actual aspect ratio (`aspect-ratio: 3 / 2`, i.e. 6:4), not a fixed percentage of the hero's width.** First built as a flat `flex: 0 0 60%`/`flex: 0 0 40%` split with `.hero-content`, which forced a roughly 1.9:1 box — much wider/flatter than the real photo's 3:2 shape, so `background-size: cover` on `.hero-slide` was cropping a meaningful chunk off the sides. Changed to: `.hero-media { height: 100%; aspect-ratio: 3 / 2; }` (width now derived from the fixed hero height via that ratio, instead of a percentage), `.hero-content { flex: 1 1 auto; min-width: 0; }` (takes whatever width is left over). Because the box's proportions now exactly match the photo's own, `cover` shows the whole image with no cropping — this only works because the actual hero photos are genuinely 6:4/3:2; if that source ratio ever changes, this value needs to change with it, or cropping comes back. Same `aspect-ratio: 3 / 2` reapplied in the `max-width: 720px` stacked-mobile layout (`.hero-media { width: 100%; height: auto; aspect-ratio: 3 / 2; }`, replacing what used to be a fixed `220px` height there) — same reasoning, just full-width instead of full-height as the fixed dimension.
- **`#home-search-input`/`#home-search-results` moved inside the hero itself** (`.hero-search`), not sitting in a separate section below it any more — same IDs, same shared search index/wiring as before (`js/main.js` is ID-based, not positional, so relocating the markup needed zero JS changes). Styled distinctly for the dark hero background (`.hero-search-input` — `var(--glass-bg-dark)`/`var(--glass-border-dark)`, white text, not the light-background `.photo-search-input` used elsewhere) but still reuses `.home-search-results`'s card styling for the dropdown itself, just repositioned via the higher-specificity `#home-search-results.hero-search-results` (an ID-qualified selector, not just a second class — guarantees the position/margin overrides win regardless of which block ends up later in the stylesheet, unlike a plain second class which would be order-dependent). Still one combined index shared with the header overlay (site pages + every photo) — the "don't have two different 'here's the archive' devices stacked on top of each other" lesson from the previous iteration (a "Recently added" strip, dropped in favour of a search box) still applies; there is still only ever one visible search entry point on the homepage, just relocated.
  - **`.hero`'s `overflow` had to change from `hidden` to `visible`** for the results dropdown to actually show — `.hero-media` clips its own photo with its own `overflow: hidden` already, so `.hero`'s outer overflow wasn't load-bearing for that any more (it was, back when `.hero-slide` was a direct absolutely-positioned child of `.hero` itself, before the hero-content/hero-media split — just never revisited once that stopped being true). Verified directly (Playwright: fill the search box, confirm the results box's bottom edge extends below the hero's own bottom edge and is still visible) rather than assumed safe.
  - `js/main.js`'s `initSearch()` was refactored so both search boxes share one index and one render function (`renderResultsInto`/`wireSearchBox`) instead of the overlay owning all the logic — needed once a second box existed on the same page, so `PHOTOS_DATA_PROMISE` isn't fetched/mapped twice and a fix to result-rendering only has to happen in one place. `wireSearchBox` no-ops on missing elements, so `index.html` is the only page where the homepage box's wiring does anything.
  - Empty-state differs deliberately: the header overlay shows a hint ("Search the village website — try…") when opened with no query, since it's a modal that otherwise looks blank; the homepage box shows nothing until you actually type (`.home-search-results:not(:empty)` in `css/style.css` only draws the dropdown's card/border once there's content) — an empty-but-boxed dropdown sitting in the hero would look like a broken/empty panel rather than an unused search box.
  - **A search result whose URL is absolute (`http://`/`https://`) opens in a new tab** (`renderResultsInto` in `js/main.js`) — the Facebook group's `SITE_SEARCH_INDEX` entry is the only one of these today. Bug, fixed: every hand-written Facebook link elsewhere on the site (footer, homepage callout button) already had `target="_blank" rel="noopener"`, but this one is built dynamically (`document.createElement("a")`), which never had that attribute set — so finding it via search, unlike every other route to it, navigated the visitor away from the site entirely instead of opening a new tab.
  - **A photo's search excerpt (`js/main.js`, `photoEntries.map`) only shows "Credit: …" when `photo.credit` is both set and not the "—" placeholder.** Bug, fixed: the condition used to be just `p.credit !== "—"` with no truthy check first — harmless for Drive-synced photos (they always get a default `"Unknown — needs a credit"` string) but for a photo added straight through the CMS with the Credit field left blank, `p.credit` is `undefined`, and `undefined !== "—"` is still `true`, so the excerpt printed the literal text "Credit: undefined". Caught on a real photo ("The Harrow Inn," added via the admin with no credit filled in) — the fix (`p.credit && p.credit !== "—" ? ... : null`) matches the truthy-check pattern already used everywhere else this same "Credit: X" text gets built (`js/place.js` twice, `js/map.js` once) — this was the one place that pattern had been missed.
- **The map is no longer promoted on the homepage at all, in either form.** It first went from a full embedded live map to a small `.callout-map` teaser card (static SVG illustration, "Explore the interactive map →" button) sitting below the "Photo archive" category tiles — that card was later removed outright, since the hero's own "See the interactive map" button and its lede paragraph ("...explore the interactive map of buildings that used to stand in the village...") already cover it, and a second dedicated pitch further down the page was judged redundant once the hero carried that message. `index.html` still doesn't load `vendor/leaflet/leaflet.css`, `vendor/leaflet/leaflet.js`, `js/map-categories.js`, or `js/map.js` — none of that was ever needed there. (`js/photos.js` is still loaded, for the search box's photo results and category tile images.) **The `id="map"` anchor on `index.html` is gone along with the card it was on** — an old bookmark/link to `index.html#map` now just lands at the top of the homepage rather than scrolling anywhere in particular; nothing in this codebase still links to that fragment (checked directly), so this is a one-time, accepted regression for anyone with an old external bookmark, not an active link left dangling.
- **`map.html`** is the full experience that used to live on the homepage, moved essentially verbatim — same `#historic-map`/`#map-filters`/`#map-list` structure, same "know a building" form, same script includes (`js/photos.js` for the auto-generated-pin data, `vendor/leaflet`, `js/map-categories.js`, `js/map.js`) as `category.html` already uses, just not locked to a category (`window.LOCKED_CATEGORY` unset, same as the old homepage map). If you touch the map's markup/behaviour, `map.html` is now the place — not `index.html`.
- Every link that used to point at `index.html#map` (footer "Explore" list on all pages, `js/search-index.js`'s map entry) points at `map.html` directly — so visitors land on the real thing, not a homepage teaser (which no longer exists to land on anyway, see above).
- **"Historic Map" was renamed "Interactive Map" everywhere** (nav/footer links, page title, headings, `js/search-index.js`'s entry, `aria-label`s) — requested explicitly, to describe what it actually does rather than its subject matter. The `#historic-map` element id (the Leaflet container, in `js/map.js`/`category.html`/`map.html`) and internal comments referring to "the historic map" as a feature were **not** renamed — only user-visible text and doc-comments meant for a human reader change; renaming the id would mean also touching `js/map.js`, for a purely cosmetic gain. If you add new user-facing text about this feature, call it "Interactive Map" (or "interactive map" mid-sentence), not "Historic Map."

There is no photo lightbox/modal on `index.html`/`category.html` any more — clicking any photo thumbnail (grid, map popup) navigates straight to `place.html?photo=ID`, a real page. The only remaining modal on the site is the small "Know more about this photo?" popup on `place.html` itself (`.place-know-more-modal`, opened by `#place-know-more-btn`) — don't reintroduce a full-photo lightbox; that pattern was deliberately replaced because it was confusing for a non-technical user testing the site.

`js/photos.js` and `js/map.js` are shared by every page that uses them (`js/map.js`: `category.html` and `map.html`; `js/photos.js`: those two plus `index.html`, for the recent-photos strip and category tile images). A page sets `window.LOCKED_CATEGORY = "streets"` (etc.) in an inline `<script>` before loading them to lock both to one category; `map.html` doesn't set it, so it shows everything, the same way `index.html`'s embedded map used to before it moved there. Don't fork these scripts per-page — extend the shared ones.

## Categorisation rule — always read from the Drive folder structure

A photo's category (`streets`, `people`, `events`, `nature`, `aerial`, `other`, `churches`, `groups`, `industry`, `schools`, `sports`) is decided **only** by which Drive subfolder it was uploaded into — that's what `CATEGORY_FOLDERS` in `automation/drive-photo-sync.gs.js` encodes, and it's already correct in `data/photos.json`.

**Never recategorise based on what's visually in the photo.** The folder is the only signal that counts, in both directions:
- A photo uploaded to "Streets & Buildings" stays `streets` even if a person appears in it.
- A photo uploaded to "People" stays `people` even if a building is visible behind them, and a photo uploaded to "Events" stays `events` even if it's mostly one person's portrait — the split between the two is itself a judgement call made once, at upload time, by whoever's filing it; it isn't something this codebase should try to re-derive later from a caption or a photo's contents.

`people`/`events` started as one Drive folder ("People & Events") and got split into two ("People" and "Events") — `CATEGORY_FOLDERS` still maps the old folder name too, so nothing breaks if that Drive folder hasn't actually been renamed/split yet. Existing photos already categorised `people` were **not** retroactively reclassified into `events` when this split happened — that would mean guessing at photo content, which is exactly the thing this rule exists to prevent. They can be moved by hand later, by someone who can actually see what's in them, via the Category dropdown on that photo's own entry — see "Recategorising a misfiled photo" below.

When adding or editing anything that assigns a category by hand (e.g. `data/map-pins.json` entries for the Interactive Map), copy the category straight from that photo's existing entry in `data/photos.json` rather than guessing from the subject matter.

**An empty category shows its own plain message** — `category.html`'s `js/photos.js` (`renderGrid`) shows "No photos in this category yet — check back soon, or explore another category" whenever a category has zero photos. This grid is a plain "browse this category" view, capped to the most recent `PREVIEW_COUNT` with a "show all" button (see "category.html's search box" below for why it's no longer search-filtered) — the empty message is purely about the category having nothing in it yet, not about any search.

**`category.html`'s "Looking for something specific?" box is the shared site-wide search, not its own filter.** It used to run its own separate match-and-filter over just that page's `#photo-grid` (`js/photos.js`'s own `matches()`/query handling) — reported as simply not working, and not reproducible in testing, so rather than keep debugging a bespoke implementation it was replaced outright with the exact same mechanism already proven to work on the homepage hero box and the header's search overlay: `#photo-search-input` + a new `#photo-search-results` dropdown (`.home-search-results` styling, reused as-is), wired through `js/main.js`'s shared `wireSearchBox()`/`renderResultsInto()` (see "Homepage" above) as a third box alongside those two. This means it now searches the **whole site** (every photo, every category, plus `SITE_SEARCH_INDEX`'s static pages) rather than just the current category, and results are a click-through dropdown rather than the grid re-filtering itself in place — the placeholder text ("Search the whole photo archive…") was updated to match. The `#photo-grid` below is now unaffected by anything typed into this box.

## General rule: a photo's Drive folder decides how it's used, full stop

This applies beyond just category. Whatever folder a photo is uploaded into determines its role according to that folder's defined behaviour in `automation/drive-photo-sync.gs.js` — never assume a photo can serve double duty across folder purposes just because the same underlying file happens to sit in two folders.

Concretely: **Hero images** photos are for the homepage banner (`data/hero.json`) only. Even when the exact same Drive file is also uploaded to a category folder (so it's also in `data/photos.json`), it must not show up in the photo archive, its category tiles, or site search — `js/photos.js`'s `PHOTOS_DATA_PROMISE` filters archive photos against `data/hero.json` by filename (not full path, since the two pipelines resize the same file into different folders — `images/photos/` vs `images/hero-photos/` — under an identical filename) to enforce this. If a new dedicated folder is ever added to the sync script, give it the same treatment: figure out what "belongs only to that folder's purpose" means, and exclude it from other surfaces rather than letting it leak across by default.

## Caption cleanup — filename becomes caption, minus Dad's filing codes

Dad's Drive filenames often carry his own archival codes — a leading catalog number ("003 ...") and/or a "MOT 1-11" style reference. `cleanCaption()` in `automation/drive-photo-sync.gs.js` strips both of those (and only those) before the filename becomes a photo's public caption, e.g. "003 Generous Briton c1936 MOT1-11.jpg" → caption "Generous Briton c1936". Don't strip anything else speculatively (parenthetical notes, credit-looking words, etc.) — those are still part of his description and might be meaningful.

The untouched original filename is never discarded: it's stored verbatim in that photo's `ref` field in `data/photos.json` and shown as a small "Ref: …" tag on the photo's own page (`.place-photo-panel-ref` in `js/place.js`), and it's included in the photo search haystack too, so searching his catalog number or MOT code still finds the photo.

## Map pins come from two sources — don't require a manual step for either

`data/map-pins.json` (`{ "pins": [...] }`) is a small hand-curated list, editable via the admin (richer written descriptions, for pins worth a proper story). But most located photos get their `lat`/`lng` automatically, via an "@lat,lng" in the filename or a recognised place subfolder (see `KNOWN_PLACES` in `automation/drive-photo-sync.gs.js`) — those must **not** require someone to also hand-add a curated pin, or pins silently go missing (this happened once: 5 photos had coordinates, only 2 showed on the map, because 3 were never added to the curated list).

`js/map.js` fixes this by fetching `data/map-pins.json` and merging it with an auto-generated pin for every other photo in `data/photos.json` that has `lat`/`lng` and isn't already covered by a curated entry (matched by `photoId`). Keep it this way — if you ever touch map pin logic, a located photo appearing on the map should never depend on a manual `data/map-pins.json` edit.

Curated pins store their location as one `coords` string field (e.g. `"52.679363, -1.097994"`) rather than separate `lat`/`lng` numbers — deliberately, to match the copy-paste-from-Google-Maps workflow (right-click a spot, click the coordinates that pop up to copy). `parseCoords()` in `js/map.js` splits it back into `lat`/`lng` at load time. Photos use the same `coords` string convention in their own per-file storage (see "Photos: one file per photo" below) — but `data/photos.json`, the generated aggregate, still gets plain numeric `lat`/`lng` per photo, unchanged from before; `scripts/rebuild-photos-index.js` does that `coords` → `lat`/`lng` conversion at build time, so `js/photos.js`/`js/map.js` never had to change.

Every marker has both a **hover tooltip** (`.bindTooltip(item.name, ...)`, in `js/map.js`'s `addMarkers` and `flyToPhotoLocation`) and a **click popup** (`.bindPopup(...)`, the existing full-detail card) — two separate, independently-triggered Leaflet bindings on the same marker, not one thing that does both. Requested explicitly so a visitor can see what a pin is just by pointing at it, without committing to a click to find out. Kept deliberately terser than the popup (just the name, no category badge/photo/description) — it's a quick "what's this," the popup is still the place for the full detail. Themed via `.leaflet-tooltip`/`.leaflet-tooltip-top::before` in `css/style.css`, matching the existing `.leaflet-popup-content-wrapper` glass styling rather than Leaflet's plain default tooltip box.

`js/map-categories.js` holds only `MAP_CATEGORIES` (the fixed colour/label taxonomy) — that one's a genuinely static lookup table, not editorial content, so it stays as plain JS rather than a CMS-editable file.

## Photos: one file per photo, plus a generated aggregate

`data/photos/<id>.json` (one file per photo, e.g. `data/photos/1RjrLTG9-003-generous-briton-c1936-mot-1-11.json`) is the real, CMS-editable source of truth — analogous to `data/pages/<slug>.json`. `data/photos.json` is a **generated aggregate**: a plain bare array, in exactly the shape it's always been, which is the single file every front-end script (`js/photos.js`, `js/map.js`, `js/place.js`) and the admin previews actually fetch. Never hand-edit `data/photos.json` directly — it gets overwritten.

`.github/workflows/rebuild-photos-index.yml` + `scripts/rebuild-photos-index.js` regenerate `data/photos.json` automatically on every push that touches `data/photos/**` (a Drive sync or a CMS save), sorting newest-first by each photo's `addedAt` ISO timestamp, and commits the result straight back to `main`. `automation/drive-photo-sync.gs.js`'s `appendMetadataEntry` (new photo) writes directly to a single `data/photos/<id>.json` file rather than reading/writing the whole array — cheaper, and it's what makes the file safely CMS-editable without a giant merge-conflict-prone list.

This split exists for the same reason `PREVIEW_COUNT` caps the homepage archive grid: the admin has to stay usable at hundreds/thousands of photos, so photos get their own **folder collections** (the six `photos_*` collections in `admin/config.yml`, one entry per file, picked by caption — see "Photos: one collection per category" below for why there are six rather than one) rather than a single big `list` widget like `map-pins.json`'s (fine there, since that list stays small and hand-curated).

**This CMS's folder/file collections silently drop any field not listed in `config.yml`'s `fields:` on save.** Each `photos_*` collection therefore lists every field that exists on a photo — including ones that shouldn't normally be hand-edited (`id`, `ref`, `addedAt`) — labelled "Internal" with a hint rather than truly locked (no fully reliable read-only widget). If you ever add a new field to the photo schema, add it to all six collections, or it'll vanish the next time a photo in the collections missing it is saved through the CMS.

**Adding a photo straight through the admin** — `create: true` on each `photos_*` collection, with `src` as an `image` widget (upload lands in that collection's own `images/photos/<category>/`, the same folder Drive-synced photos in that category use) so "upload the file, then fill in the details" works in one form. Three fields are deliberately left for the human to skip rather than compute, and `scripts/rebuild-photos-index.js` fills them in at build time instead of asking someone to hand-type them (and, since it edits the per-file JSON directly when it does, the fix sticks — it isn't redone from scratch on every rebuild):
- `id` — always overwritten with the entry's own filename (`file.slice(0, -".json".length)`), never trusted from the file. New entries get a unique filename for free from the collection's `slug:` template (`{{year}}{{month}}{{day}}{{hour}}{{minute}}{{second}}-{{slug}}`), so nobody has to invent an ID by hand.
- `ref` — if left blank, defaults to the uploaded image's own filename (`decodeURIComponent(path.basename(photo.src))`) **and is written back to that photo's own file**, not just the generated aggregate. Drive-synced photos already set a richer `ref` (Dad's original, uncleaned filename) themselves, so this fallback only ever fires for a photo added through the CMS. **Bug, fixed**: this write-back was missing for a while — the fallback value was computed for the aggregate only, so the live site's "Ref:" tag was always correct, but the admin's own "Internal — reference code" field stayed blank forever on a CMS-added photo (contradicting its own hint text, "it's filled in automatically... if you leave this blank"), forcing a manual re-type every time someone opened that entry to check it. Caught because a real photo (the DCE aerial shot) hit exactly this — its `ref` had to be typed in by hand before the fix landed. Now mirrors the `addedAt` pattern below exactly: computed and written back **before** the coords → lat/lng conversion further down (aggregate-only, would corrupt the per-file schema if it ever leaked into a write-back — see below), consolidated into one `fs.writeFileSync` shared with the `addedAt` backfill via a `dirty` flag, rather than two separate writes.
- `addedAt` — if left blank, backfilled with the current time **and written back to that photo's own file**, not just the generated aggregate, so it's set once and stays stable (a naive "default to now" only in the aggregate would make that photo look newer on every unrelated rebuild, since "now" keeps moving). This is also why `.github/workflows/rebuild-photos-index.yml` stages `data/photos/` as well as `data/photos.json` in its commit step.

## Every photo gets its own page — `place.html?photo=ID`

Every photo in the archive has a real, dedicated page — not just ones with a hand-written story. Clicking any photo thumbnail (grid, map popup) navigates to `place.html?photo=<id>`. There is no modal/lightbox for viewing a photo any more; this was a deliberate architecture change (the old click-to-open-a-modal pattern was confusing for non-technical users) — don't reintroduce one.

`js/place.js` treats `?photo=ID` as primary and `?slug=X` as optional/derived:
- If only `?photo=ID` is given, it looks up that photo, and — if that photo's own `pageSlug` field is set — also fetches that page's `data/pages/<slug>.json` for its extra written content. If `pageSlug` isn't set, the page still renders fine with just the photo's own facts (no page, no blocks).
- `?slug=X` can also be passed explicitly (e.g. from an old link, or a pin with a `pageSlug` but no specific photo in mind) — in that case the page falls back to rendering just the page content, without a photo panel, if there's no `?photo=` too.
- A photo with no `pageSlug` at all still gets a perfectly good page: photo, facts, History (if set), and the "Know more" button — it just has no extra blocks/written-story section beneath.

**`data/pages/<slug>.json`** (a *Story page* — optional extra content, not required for a photo to have a page) — one file per page: `{ "title": "...", "blocks": [...] }`. Each block has a `type` of `text` or `photo`:
  - `text`: `{ "type": "text", "text": "..." }` — rendered by `js/place.js`'s tiny built-in markdown-lite (paragraphs on blank lines, `**bold**`, `*italic*`, `[label](url)` links). Not a full markdown library on purpose — this is a static, no-build-step site, so no npm dependency was added for it. Don't casually extend the syntax without checking `renderInline`/`renderTextBlock` in `js/place.js` can actually handle it.
  - `photo`: `{ "type": "photo", "photoId": "..." }` — must match an id in `data/photos.json`; renders as a thumbnail linking to that photo's own page (`place.html?photo=ID`). There's no admin UI for Story pages any more (see "Story pages" below) — this only matters if you're hand-editing a `data/pages/*.json` file directly. A photo's `id` is never shown anywhere on the live site (only `ref` is, as the "Ref:" tag) — look it up in `data/photos/<id>.json` (the filename) if you need it.
- A photo's `pageSlug` field (the filename of the Story page, minus `.json`) is what opts it into showing a Story page's extra content — but there's deliberately **no field for it in the Photos admin collection any more** (removed at the user's request: every photo already gets its own full page automatically, so a per-photo "attach a story page" step just added confusion for no real benefit for a family archive with one non-technical uploader). A handful of photos from before that change still have `pageSlug` set in their own `data/photos/<id>.json` and keep working exactly as described above — don't strip it from them. Going forward, the supported way to give a *place* extra written content is a Map pin's own "Full story page" field (see `map_pins` below), not a per-photo link.
- On `place.html`, the page is built up in this order, each piece skipped silently if there's no photo (bare `?slug=X`) or the relevant field is empty:
  - A **prominent location banner** (`.place-location-banner`, `js/place.js`'s `renderLocationBanner`) — "This is one of *N* photos of **`<location>`** — see the full history and timeline →," linking to that place's `location.html` page (see "Location timeline" below). Only shown when 2+ photos share this one's `placeKey` (see below — a lone photo has no timeline to link to). Sits right at the top of the content, above the facts panel — added because the "More photos from…" grid further down the page (already existed, see below) turned out to be too easy to actually notice; a real case (two genuine photos of the Harrow Inn, 1913 and 2002) were already being cross-linked by it correctly, but the user never found that link until told where to look.
  - A **facts panel** (`.place-photo-panel`) at the top — caption, date/location, category/credit, ref, and (if the photo has coordinates) a small live preview map (`#place-mini-map`, `js/place.js`'s `renderMiniMap`) with that photo's pin, plus an "Explore the full map →" link. Both the mini-map (click anywhere on it) and the link go to `map.html?photo=ID`, which `js/map.js` picks up via its own `?photo=` param on load to fly to and highlight that same pin — `place.html` no longer loads a full map itself (see "Homepage: photo-archive-first" for why the map lives on its own page), just this compact, deliberately non-pannable/non-zoomable preview (dragging/scroll-zoom/double-click-zoom all off — it's a preview, not a navigable map). Added back after the homepage redesign, since losing an at-a-glance "where is this" view entirely (not just off the homepage, but everywhere) turned out to be a real regression, not just a decluttering win. The panel's **main photo itself is clickable** — opens a full-screen zoom/pan viewer, see "Full-screen photo zoom" below.
  - **History** (`.place-history`) gets its own full-width, light-background section directly under the facts panel, not folded into it — a light background reads better for a longer paragraph than the panel's narrow dark info column did, which is also why it's not just left inside `.place-photo-panel-info` alongside the terser caption/date/credit/ref facts.
  - A **"Know more about this photo?" button** (`#place-know-more-btn`) — opens the submit form in a small popup (`.place-know-more-modal`) rather than showing it inline on the page; see "Know more" below.
  - The Story page's own `blocks` (the extra written content, if a Story page is linked) — labelled just "Content" in the admin, since the facts above already cover caption/date/location/etc., this is only for anything beyond that.
  - A **"← Back to `<Category>`"** link (`#place-back-link`, in the page-hero) pointing at `category.html?cat=X` — lets a reader get back to the archive they came from.
  - A **"More photos from `<location>`"** grid (`.place-related`) listing every other photo sharing this one's `placeKey` (see below). Deliberately kept alongside the new location banner above rather than removed — the banner is the "go look at the whole timeline" nudge, this grid is a quicker "here are the actual sibling photos, inline, no extra click" for someone who's already scrolled past it reading the rest of the page; not fully redundant with each other.

## Location timeline (`location.html`)

Requested explicitly, after the "More photos from…" grid (above) turned out to solve the *linking* problem but not the *presentation* one — the user wanted something closer to a small dedicated page per place: the shared history, and every photo of it in date order, not just a grid of thumbnails at the bottom of one specific photo's page. Reachable from the location banner on any photo page (see above) via `location.html?loc=<key>`.

- **`placeKey(photo)`** (`js/main.js`, shared by `js/place.js`'s banner/related-photos grid and `js/location.js`, so all three can never disagree about which photos belong together) is a photo's "place identity," checked in three tiers:
  1. **`placeId`** (admin: "Same place as another photo (if it won't link up on its own)," every category, optional) — a manual override, for when neither of the two automatic tiers below can bridge two photos of the same real place. The case that motivated adding it: a street renamed over time (a real example — Melton Road used to be Main Street) means an old photo's Location text can be a *completely different, equally correct* string from a modern photo of the same building, and if nobody's pinpointed the old photo's coordinates either (very plausible for an old archive photo), it has no automatic way to match at all. Typing the exact same text into `placeId` on both photos (any text — a building's name is the obvious choice) forces them together regardless of what their coordinates or Location say. Deliberately left off `automation/drive-photo-sync.gs.js` — this is a rare, manual, human-judgement call, not something to guess at automatically.
  - **Field renamed and reworded, code unchanged**: this was originally labelled "Internal — manual place grouping," the same "Internal —" prefix used by `ref`/`id`/`addedAt` — three fields that genuinely are auto-filled and meant to be left alone, whose hints all open with "Leave blank." Reported as confusing in practice: someone filling in photos by hand had no reason to think this one "Internal" field was actually theirs to use sometimes, so the Melton Road/Main Street case kept going unlinked not because the mechanism didn't work, but because nobody knew to reach for it. Renamed away from the "Internal —" convention and reworded to lead with *when* to use it (the concrete renamed-street scenario) rather than opening with "Leave blank" — same field name (`placeId`) and behaviour, wording only. The **Google Maps coordinates** field's hint was strengthened the same way, to say outright that coordinates are what link photos of the same place together (not just what places a pin on the map) — since that's the main automatic tier and the thing worth reaching for before this override.
  2. **GPS coordinates** (pasted from Google Maps) — two photos of the same physical spot almost always share identical coordinates, even when their Location text varies in wording (a real example: three Harrow Inn photos all share one exact coordinate, but one read "The Harrow Inn, Melton Road, Thurmaston" while the other two read "The Harrow Inn, Melton Road" — no ", Thurmaston" — an exact-text match silently left that one out of the group, which is what actually got reported as "grouping is causing some frustration"). Rounded to 5 decimal places (~1m of precision) rather than compared as raw strings, so two coordinates pasted at slightly different precision still match.
  3. **Location text** — only consulted when a photo has neither of the above. First built purely on this tier (via `slugifyText`, now used only by `events.html`/`event.html` for their event-name grouping) — the same "grouping is automatic, no extra admin step" idea as Events' folder-driven grouping, before the Harrow Inn case above showed text alone wasn't enough.
  
  Returns `"manual:<slug>"`, `"geo:<lat>,<lng>"`, `"loc:<slug>"`, or `null` for a photo with none of the three — this string doubles as the `?loc=` URL value directly (`encodeURIComponent`-wrapped), no separate slug step.
- **A place-key group isn't guaranteed to have Location text on every photo in it** (a coordinate-only match can pull in a photo that never had Location typed, or vice versa) — `js/place.js`'s `placeLabel`/`js/location.js`'s own equivalent pick the first non-empty `location` text found across the group (preferring the anchor photo's own) to use as the human-readable heading, falling back to "this place"/"This place" only if truly nobody in the group has one.
- **`js/location.js`** fetches `PHOTOS_DATA_PROMISE` (loading `js/photos.js` purely for that promise — its own `DOMContentLoaded` handler no-ops safely on `location.html` since none of `#photo-grid`/`#photo-filters`/etc exist there), filters to photos whose `placeKey(p)` matches `?loc=`, and renders one entry per photo: thumbnail, caption (linking to that photo's own `place.html?photo=ID` for zoom/the mini-map/etc — this page doesn't duplicate those), date, credit, and that photo's own History in full.
- **Also downloadable as its own combined PDF** — one file covering every photo at this place, not just links out to each one's individual PDF. See "PDF generation" below for the shared mechanics; `orderPhotos()` here is the one source of truth both the HTML timeline and the PDF sort from, so they can't drift apart.
- **Sorted chronologically by year, not by upload order** (`extractYear`, in `js/main.js`, shared — see "Events" below for its other caller) — pulls the first 4-digit number out of the `date` field ("1913" → 1913, "c.1936" → 1936, "2002" → 2002). **Explicitly excludes the `"Added <Month> <Year>"` placeholder** used everywhere else on this site for a photo whose real date isn't known (`automation/drive-photo-sync.gs.js`, the Photos admin form's own hint text) — that string is *when it was uploaded*, not anything about the photo's actual subject, and a naive regex would happily (and wrongly) pull the year straight out of it, placing an unknown-date old photograph as if it were the most recent thing in the timeline. Photos matching that placeholder are held out into a separate "Date unknown" group at the end instead, under its own `<h2>`.
- **History is rendered as real paragraphs, not one run-on line** — `formatMultilineText(str)` (`js/main.js`, shared) splits stored text on blank lines into one escaped `<p>` per paragraph. This surfaced a **pre-existing gap fixed at the same time**: `js/place.js`'s own `renderHistorySection` (an individual photo's own page) had exactly the same bug — a photo's multi-paragraph History (a real example: the 1913 Harrow Inn photo's history runs to five distinct paragraphs) was being dropped into a single `<p>` with `escapeHtml()`, so every paragraph break in the stored text silently collapsed into a run-on wall of text. Fixed there too, using the same shared helper, rather than only fixing it for the new timeline page and leaving the two views of the same text inconsistent with each other.
- Not-found state (`#location-not-found`) covers both a missing `?loc=` param and a slug matching zero photos (e.g. a stale/mistyped link) — same "don't crash, just say so" pattern as `place.html`'s own not-found state.

## Events: `events.html` (list) + `event.html?event=<id>` (one Event Page)

Requested once the Events category alone (a flat grid, same as every other category) wasn't enough for something like Remembrance Day — an occasion with several photos and a story worth telling together, not just a pile of individually-uploaded Events photos.

**Went through two designs before landing here — both worth knowing about since they explain some naming choices:**
1. First built as folder-driven grouping (a photo's folder decided which event/year it belonged to, mirroring how category itself works) — but the user found this "hasn't quite worked as I want," and it turned out the real need was simpler: **one entry covering a whole occasion — description and every photo of it, uploaded together — not automatic grouping of separately-uploaded individual photos at all.**
2. That folder-driven mechanism (a nested `photos_events` Decap collection, `automation/drive-photo-sync.gs.js`'s two-level Events folder walk, `rebuild-photos-index.js` deriving `eventName`/`eventYear` from a photo's own path) has been **fully reverted** — none of it exists any more. If you see any of those names mentioned elsewhere (old commit messages, etc.), they're history, not current behaviour.

**Current design — "Event Pages," a whole occasion as one entry:**

- **`admin/config.yml`'s `event_pages` collection** (`data/events/<id>.json`, separate from the six `photos_*` collections) — one entry per event *occasion* (e.g. "Remembrance Day Parade 1975"; the same recurring event in a different year is a separate entry, e.g. "...1980" alongside it — there's no automatic cross-year grouping, each occasion is independent). Fields: event name, date, description, optional Location/Google Maps coordinates (see "wired onto the interactive map" below), and **`photos`, a `list` widget of a single bare `image` field** (`photo.photos` ends up a plain array of path strings — `["/images/events/a.jpg", "/images/events/b.jpg"]` — not an array of objects). This is deliberate, not the simplest-looking option: Decap's list widget only supports **selecting several images at once in the media library and adding one list item per file automatically** when the list holds one plain field, not an object with multiple sub-fields — an object shape (`{ image, caption }`, tried first) forced one-at-a-time uploads despite looking almost identical in the config, which is exactly what was reported as "still can't bulk upload" after the first version shipped. The trade-off accepted for this: **no per-photo caption any more** — the event's own name/date/description covers it instead. The older flat `photos_events` collection (renamed "Events (single photos)" in its label) still exists, for a one-off Events photo with no write-up of its own — the two are deliberately separate collections with different jobs, not one replacing the other.
- **`scripts/rebuild-events-index.js`** builds `data/events.json` from `data/events/*.json` — same shape of job as `rebuild-photos-index.js` (id from filename, coords → lat/lng, backfill+persist `addedAt` once, sort newest-first), kept as its own script since an Event Page's shape (one description, a whole list of photos) is genuinely different from a photo's. Wired into the same `.github/workflows/rebuild-photos-index.yml` (triggers on `data/events/**` too) rather than a separate workflow, since it's the same "regenerate a derived aggregate and commit it back" job. **The `data/events/` directory may not exist at all yet** (no Event Pages ever created) — the workflow's `git add` guards for this (`git add data/events/` on a path that doesn't exist at all is a fatal, whole-command-failing error, unlike a photos-only push where `data/photos/` always exists), and the script itself writes an empty `data/events.json` (`[]`) rather than erroring when the directory is missing.
- **`events.html` / `js/events.js`** fetches `data/events.json` directly (no grouping logic needed — each entry is already a distinct occasion) and renders one tile per Event Page (reusing `.photo-filters` styling — cover photo is the entry's first photo, meta line is date + photo count), linking to `event.html?event=<id>`. A plain "Browse single Events photos →" link points at the old flat `category.html?cat=events` grid for one-off photos not part of an Event Page — no attempt to merge the two into one list, since they're different kinds of content.
- **`event.html` / `js/event.js`** renders one Event Page: heading/date/photo count, the description (`formatMultilineText`, same paragraph-splitting as `location.html`'s History) in a `.place-history` block, then every photo as a `.photo-grid` of buttons (not links — these photos have no individual page of their own to navigate to). Clicking one opens the **exact same full-screen zoom/pan overlay `place.html` uses for its own main photo** (`.place-zoom-overlay`, `vendor/panzoom`) — duplicated into `js/event.js` rather than shared as a module, since `js/place.js`'s version is wired to a single fixed photo via closures, not a list of many.
- **Wired onto the interactive map** when an Event Page has Google Maps coordinates — `js/map.js` fetches `data/events.json` as a third source alongside curated `data/map-pins.json` pins and geotagged photos, adding a pin (the existing "events" category colour, `MAP_CATEGORIES.events`) whose popup uses the Event Page's own first photo as its thumbnail and links to `event.html?event=<id>` rather than a `place.html` page. `popupHtml`'s link-building was generalised into one `itemHref(item)` helper (`eventId` → `event.html?event=`, else `photoId` → `place.html?photo=`, else `pageSlug` → `place.html?slug=`) so this didn't mean a parallel, diverging copy of the popup-building logic.
- **No PDF export** — not asked for, and the `location.html` pattern (`js/pdf-helpers.js`) already exists if it's wanted here later.
- **The homepage's Events category tile falls back to an Event Page's photo if there's no flat "Events (single photos)" photo to use.** Bug, fixed: `js/photos.js`'s `setCategoryTileImages()` only ever scanned `allPhotos` (`data/photos.json`, i.e. the flat per-photo collections) for a `category === "events"` match — so a village with real Event Pages full of photos but zero individually-uploaded Events photos saw a genuinely blank tile, despite "there being event photos." Event Page photos live in a separate array (`data/events.json`'s `photos`), not as individual `category`-tagged entries, so they were never in `allPhotos` to begin with. Fixed by falling back, for the `events` tile specifically, to a small dedicated `fetch("data/events.json")` that picks the newest Event Page with at least one photo (`events.json` is already sorted newest-first) — same "most recently added" convention the other five tiles already follow, just sourced from the other collection when the usual one comes up empty.

## Full-screen photo zoom

Requested after a high-resolution aerial photo was added and the detail was worth examining closely — but built for **every** photo's page, not just Aerial, since it's generally useful. Clicking the main photo in `.place-photo-panel-media` (`cursor: zoom-in`) opens `.place-zoom-overlay`, a full-screen dark viewer with the same image, zoomable/pannable via [vendored `panzoom`](https://github.com/anvaka/panzoom) (`vendor/panzoom/panzoom.min.js`, MIT — fetched the same no-build-step way as Leaflet/jsPDF/qrcode-generator: `npm install panzoom@9 --no-save`, copy the UMD dist file out of `node_modules`, no bundler involved). Chosen over hand-rolling pan/zoom because pinch-gesture math across mouse/wheel/touch is exactly the kind of thing worth not reinventing.

- **A small "🔍 Click to zoom" badge** (`.place-photo-panel-zoom-hint`, bottom-right corner of the photo) makes the feature discoverable — `cursor: zoom-in` alone is invisible on a touchscreen (no hover state), which is exactly where zooming into detail matters most. `pointer-events: none` on the badge, so a tap/click on it still falls through to the `<img>` underneath rather than needing its own separate click handler — verified directly (Playwright: click at the badge's own coordinates, confirm the zoom overlay still opens). Not shown anywhere else `panzoom` isn't wired up (grid thumbnails, map popups) — it's specific to this one clickable image.

- **`js/place.js`'s `renderZoomableImage(photo)`** wires up the click (and Enter/Space for keyboard users — the trigger image gets `role="button"`/`tabindex="0"`), attaches `panzoom(zoomImage, { maxZoom: 6, minZoom: 1, bounds: true, boundsPadding: 0.15, zoomDoubleClickSpeed: 1 })` to `#place-zoom-image` on first open, and reuses that one instance on later opens (`moveTo(0,0)` + `zoomAbs(0,0,1)` to reset position/zoom each time) rather than creating a fresh instance — cheap to keep around, avoids leaking a new set of drag/wheel/touch listeners every open.
- **+ / − / Reset buttons** (`#place-zoom-in`/`-out`/`-reset`, calling panzoom's `smoothZoom`/`moveTo`+`zoomAbs`) sit at the bottom of the overlay alongside a "Scroll or pinch to zoom, drag to pan" hint (hidden below `560px` — cramped next to the close button there, and pinch is the natural first thing to try on a touchscreen anyway) — not everyone discovers scroll-to-zoom unprompted, so the buttons are the accessible/discoverable path, not just a decoration. `.place-zoom-btn`/`.place-zoom-close` use a **solid white background** (`var(--green-900)` icon/text, `box-shadow` for separation), not the translucent `rgba(255,255,255,0.12)` first tried — that was too faint to read reliably against a photo, which (unlike the rest of the site's dark-UI chrome) can be light-coloured anywhere underneath these controls; a solid background stays legible regardless of what's behind it.
- **Closing**: an ×  button, `Escape`, or clicking the backdrop. The backdrop-click check is `e.target === zoomOverlay || e.target === zoomStage` — `.place-zoom-stage` (a plain flex-centering wrapper, not itself a panzoom target) fills the *entire* overlay, so a click on the empty space around the photo lands on the stage, never on the overlay div directly; checking only `e.target === zoomOverlay` (the naive version, matching the `.place-know-more-modal` pattern elsewhere) silently never fired. Doesn't fire mid-drag/on drag-release either — panzoom is attached to the `<img>` itself (not the stage), so a pan-drag's mousedown/mouseup both land on the image as it tracks the cursor, never on the stage/overlay — verified directly with Playwright (drag the image, release over backdrop space, confirm the overlay stays open) rather than assumed from panzoom's docs.
- Deliberately **not** wired into any other image on the site (grid thumbnails, map popups, category tiles) — only the one full-size photo on its own dedicated page, where "examine this closely" actually makes sense.
- **Image quality note, since this is exactly what prompted the feature**: zoom just magnifies whatever file `photo.src` already points to — there's no separate higher-resolution asset fetched on zoom, and no AI upscaling (raised and explicitly deferred, not built — would mean wiring up a separate, likely-paid, image-enhancement service, a distinct piece of work from this). Drive-synced photos are resized to `MAX_DIMENSION = 1600` px (`automation/drive-photo-sync.gs.js`) before publishing, so zooming those in far enough will show real pixelation — expected, not a bug. Photos added **directly through the admin's upload widget**, however, currently publish at their **original, unresized dimensions** (no equivalent of `resizeViaProxy` runs for that path) — e.g. the aerial photo that prompted this feature is a full 2460×1872, with real headroom to zoom into before pixelation sets in. Don't "fix" that gap by resizing CMS uploads down to 1600px to match the Drive pipeline without checking first — it would directly work against this feature.

- **Ordinary photos** get their `location` and `history` set through the admin's **Photos** collection (see "Photos: one file per photo" below) — pick the photo by caption, fill in the field, save. A photo can alternatively get a proper entry in `data/map-pins.json` (reusing its existing `photoSrc`/`photoId` and re-pasting its coordinates as a `coords` string), which gets it a name, a description, and its own `pageSlug` editable through the Map Pins admin form, and automatically suppresses the auto-generated version of that same pin (matched by `photoId`). That's still the answer for a photo that didn't get coordinates at upload time — add/fix them there rather than needing to re-upload.

There used to be a PDF-attachment feature (a `doc` field on photos, a `document` block type on Story pages, a "View document" button) — it was removed entirely at the user's request, since it added a step that confused a non-technical editor. Don't reintroduce it; PDFs already in `documents/` were left in the repo untouched, just unlinked.

## "Know more about this photo?" — a small popup, not an inline section

Clicking `#place-know-more-btn` on a photo's page opens `.place-know-more-modal`, a small centred popup (`js/place.js`'s `renderKnowMore`) — not an inline form on the page. This was a deliberate simplification (the button-then-popup pattern reads more clearly than a form always sitting on the page) — don't turn it back into an always-visible inline section.

The form itself (`renderSubmitForm` in `js/place.js`) follows the exact same pattern as the homepage's existing "Share your memory"/"Know a building" forms: static, `action="#"`, with the same "not connected to a mailbox yet" note. Not wired up on purpose, matching those — wire all of them up together later via Netlify Forms/Formspree, not just this one. Its CSS still lives under the `.photo-lightbox-submit` class name (`css/style.css`) — kept from when this form grew up as part of the old lightbox, since every field id/label already refers to it that way; only the outer chrome (now `.place-know-more-modal`/`.place-know-more-inner`) changed. `place.html`'s modal body carries both classes (`class="place-know-more-body photo-lightbox-submit"`) so that styling still applies — if you ever rename one, rename the other in step.

The form's first field, "About this photo" (`name="photo-ref"`), is a real (not hidden) `readonly` input pre-filled with the photo's `ref` — same `photo.ref || photo.caption || photo.id` fallback chain used elsewhere for "something readable to show." Deliberately a genuine named form field, not just a `<p>` — the hidden `photo-id` field alone isn't something a human reads in a notification email once this gets wired up, so this exists purely so whoever receives that email can tell which photo it's about at a glance, without cross-referencing an internal id.

## Numbering people in a group photo (`admin/number-photo.html` + `js/place.js`)

Dad's existing routine for a group photo: number each person, post it, let people comment who's who. Built as a manual click-to-number tool, not automatic face detection — deliberately, per an explicit answer to that exact clarifying question. No computer vision, no dependency that could mis-detect or need training.

**`admin/number-photo.html` is a standalone page, not a Sveltia CMS field** — same reasoning as `admin/index.html`'s own comment about Sveltia's custom-field-type support ("unimplemented — will be added soon" at the time this was written): there's no way to build a "click on the image to drop a marker" widget inside the CMS form itself, so this had to be a separate page dad opens on the side. Two manual steps (number the photo here, paste the JSON into the CMS field) rather than one seamless one — an accepted tradeoff, not an oversight. It runs entirely client-side (`URL.createObjectURL` on the chosen file) — nothing is uploaded by this tool; the photo itself still goes through the normal Photos collection as usual, before or after numbering it here. Clicking the photo drops the next sequential marker (position stored as a percentage of the image's own dimensions, not pixels, so it stays correctly placed at any display size); clicking a marker again removes it, and everything after it renumbers down by one so the sequence always runs 1..N with no gaps — matches how numbering a photo by hand normally works, there's never a "missing number 4." The resulting JSON (`[{number, x, y}, ...]`) is copied and pasted into that photo's "Numbered people (JSON)" field, added to all 11 `photos_*` collections in `admin/config.yml` — optional, left blank on every ordinary photo.

**Rendering** (`renderNumberedPeople` in `js/place.js`, called from `renderPhotoPanel` right after `renderZoomableImage`): parses `photo.numberedPeople` as JSON, and for each `{number, x, y}` point renders a small circular `.place-photo-marker` button positioned via percentage `left`/`top` inside `.place-photo-panel-media` (already `position: relative`, pre-existing for the zoom-hint badge). Silently does nothing if the field is blank, unparseable, or empty — not an error state, just an ordinary photo with no markers.

**Reuses the existing "Know more" popup rather than a second submission mechanism.** A marker's click handler calls `e.stopPropagation()` (it sits on top of the click-to-zoom image underneath, and without this a marker tap would also trigger the full-screen zoom overlay) then `openKnowMoreModal(photo, personNumber)` — a small function factored out of `renderKnowMore` so both the plain "Know more" button and a numbered marker route through the same modal-opening path. When a `personNumber` is present, `renderSubmitForm` appends `— person #N` to the readonly "About this photo" field and swaps the intro copy to "Know who number N is?" — otherwise both read exactly as before. Same static `action="#"`/"not connected to a mailbox yet" form underneath either way; a visitor identifying someone answers through the exact same unwired-form convention used everywhere else on the site, not a parallel mechanism that would need wiring up separately later.

## PDF generation: `js/pdf-helpers.js`, shared by two pages

Both a single photo's own PDF (`place.html`) and a whole place's combined timeline PDF (`location.html`, added once the first existed and the same "open as a PDF" request came in for the timeline pages too) use [jsPDF](https://github.com/parallax/jsPDF) (vendored at `vendor/jspdf/jspdf.umd.min.js`, same no-build-step pattern as `vendor/leaflet`, MIT licensed) and [qrcode-generator](https://github.com/kazuhikoarase/qrcode-generator) (vendored at `vendor/qrcode-generator/qrcode.js`, MIT). The genuinely page-agnostic parts live in `js/pdf-helpers.js` — loaded on both `place.html` and `location.html`, after the two vendored libraries and before `js/place.js`/`js/location.js` — rather than duplicated: `SITE_URL`, `loadImageElement`, `guessImageFormat`, `downloadedDateLabel`, `buildQrPngDataUrl`, `ensureSpace`/`addPdfHeading`/`addPdfParagraph` (the low-level layout primitives), `pdfFilenameBase`, `stampPdfFooter`/`pdfFooterText`, and `openPdfInViewer` (the "open in a tab" mechanics, below). Each page's own script (`buildPhotoPdf` in `js/place.js`, `buildLocationPdf` in `js/location.js`) builds its own document-specific content on top of those.

**Opens in its own separate browser window (not just another tab in the same window) rather than forcing an immediate download**, on all three pages that generate a PDF (`place.html`, `location.html`, `chronology.html`) — requested explicitly, so the visitor decides from there whether to save, print, or just look and close it, the same controls they already know from every other PDF they've opened online. `openPdfInViewer(buildDoc, filename, btn, loadingTitle)` in `js/pdf-helpers.js` is the shared mechanism — `buildDoc` is a function returning a Promise of a finished jsPDF document (with its own `.setProperties({title})` and filename choice already made, since what makes a good title/filename differs between one photo, a whole place, and the chronology):
- **`window.open("", "_blank", "width=1000,height=1000")`** — the `width`/`height` feature string is what actually matters here, not `_blank` on its own. A bare `window.open(url, "_blank")` with no feature string just opens another tab in the current browser window in most browsers; passing an explicit size is what a browser treats as "open a genuinely separate window" instead — reported directly by the user as opening in the same window/tab before this was added, not something guessed at. Deliberately **not** adding `noopener` alongside those features — that makes `window.open()` return `null` rather than a usable window reference, which would break the rest of this function (writing the loading page into it, later navigating it to the finished PDF).
- **The tab has to be opened synchronously, inside the click handler itself, before any of the async PDF-building work starts** — `window.open()` only bypasses the browser's popup blocker when it's called directly inside a user gesture's own call stack, and building a PDF here is always async (waiting on image loads, the QR code render), so by the time the file is actually ready the call would no longer look click-initiated and get silently blocked. `openPdfInViewer` opens a blank tab immediately (with a plain "Preparing your PDF…" holding message written into it via `document.write`, so it doesn't just look like a dead blank tab for the second or two the PDF takes to build) and navigates that same tab to the finished blob URL once `buildDoc()` resolves — `pdfWindow.location = doc.output("bloburl")`.
- **If the popup is blocked anyway** (can still happen depending on the visitor's own browser settings, even with the synchronous-open trick) **it falls back to a normal forced download** (`doc.save(filename)`) rather than the PDF silently vanishing with no way to reach it. Two things feed that same fallback, not just an outright-null `window.open()`: `pdfWindow.document.close()` is called right after the holding page is written (some browsers leave the popup's document stuck "loading" without it, which can make the later `location = ...` navigation silently no-op instead of switching the tab over — this looked, from the outside, exactly like "nothing happens, no new tab" even though `window.open()` itself had succeeded); and the `pdfWindow.closed` state is re-checked immediately before navigating, inside a `try/catch`, since a tab that opened successfully can still end up closed out from under the page by the time the async build finishes (some popup blockers close it a tick after opening rather than ever returning `null`).
- **Every PDF sets `doc.setProperties({ title: ... })`** (a photo's caption, or a place's name) — Chrome's built-in PDF viewer uses a PDF's own Title metadata for both the browser tab's title and the filename it suggests if the visitor clicks its own save icon, so this is what keeps "open in a viewer, let them decide" from also meaning "whatever they save gets a meaningless blob-hash filename." Verified directly for both pages (Playwright: fetch the blob URL's own bytes from inside the new tab's JS context, confirm a real `%PDF-1.3` file with the right page count and text content, not just that navigation succeeded).

Both documents are **built by hand with jsPDF's drawing API** rather than rendering the live page to an image (e.g. html2canvas) — deliberately, so the output stays small, crisp, and text-selectable regardless of screen zoom or DPI, instead of a big flattened screenshot. The shared `ensureSpace` adds a new page whenever the next block wouldn't fit, so a photo (or a place with several photos and long History text each) still produces a clean multi-page PDF rather than overflowing.

A small QR code sits top-right on the first page ("Scan to view online," with a "Downloaded `<date>`" line under it) on both kinds of PDF — a photo's encodes that photo's own live URL (`photoPageUrl()` in `js/place.js`), a place's encodes its `location.html?loc=…` URL (`locationPageUrl()` in `js/location.js`) — so a printed copy can be scanned straight back to the right page either way. **`qrcode-generator`'s `createDataURL()` actually returns a GIF despite the name, and PDF has no native GIF image filter** — handing it to jsPDF as-is silently forces a decode-and-re-encode-as-JPEG round trip to embed it, which risks softening the sharp module edges a scanner depends on (this happened once during testing — the PDF still generated with no errors, but the embedded QR was lossy). The shared `buildQrPngDataUrl` fixes this by redrawing the GIF into an off-DOM canvas 1:1 (`imageSmoothingEnabled = false`) and reading it back out as a real PNG before it ever reaches jsPDF, so the whole path stays lossless. Don't pass `createDataURL()`'s output straight to `addImage` — always go through that conversion.

The "Downloaded `<date>`" line exists because the site's own content can change after someone downloads a PDF (a caption gets corrected, more History gets added, a new photo joins a place's timeline, etc.) — it's there specifically so a printed copy carries its own "this was accurate as of…" stamp, right next to the QR code that lets a reader jump straight to whatever the page actually says now.

**`SITE_URL` (top of `js/pdf-helpers.js`, currently `"https://www.thurmaston.com"`) is a deliberately hardcoded constant, not derived from `location.origin`/`location.host` at generation time**, even though the site itself is still only live on its temporary Netlify address — every PDF's QR code and footer contact line use it, so they already point at the *intended permanent* address rather than wherever they happened to be generated from, and don't need regenerating once the real domain goes live. This was a deliberate correction: an earlier version derived it from `location.*` for "automatically stays correct" robustness, but that's wrong here specifically because the current address is known to be temporary — a hardcoded, one-place-to-update constant is what's actually needed. **Update `SITE_URL` (and the `memories@thurmaston.com` in `pdfFooterText()`, if that ever changes too) once the real domain is live** — don't revert this back to deriving from `location.*`.

A photo image is loaded as a real `Image` element (`loadImageElement`) and handed straight to `doc.addImage` — works because every photo lives on the same origin (no CORS/canvas-taint issue to work around); a place's PDF does this once per photo, in parallel (`Promise.all`), before building anything. A photo PDF's Story-page text blocks reuse `data/pages/<slug>.json`'s raw text but strip the markdown-lite syntax (`**bold**`, `*italic*`, `[label](url)`) down to plain words rather than trying to reproduce that formatting — good enough for a printable reference copy, not a pixel-perfect mirror of the page. Note `addPdfParagraph` doesn't treat embedded `\n` line breaks as paragraph breaks the way the *HTML* rendering does (`formatMultilineText`, see "Location timeline" below) — a pre-existing gap in the PDF path specifically, not something this round touched; a multi-paragraph History still reads as one continuously-wrapped block of text in the PDF, unlike on the page itself.

The filename (used by the popup-blocked `.save()` fallback, and as the base a browser might offer when saving from its own viewer) is the photo's caption or the place's name, slugified via the shared `pdfFilenameBase` (e.g. `garden-centre-1960.pdf`, `the-harrow-inn-melton-road.pdf`) — never an internal id, which is never shown anywhere else on the site.

**`location.html`'s own "View / Print PDF" button** (`#location-download-pdf-btn`, reuses `.place-download-pdf-btn`'s styling — sized for a light background, so it sits in the light `.content-section` above the timeline, not the dark `.page-hero` where it would be nearly invisible) calls `js/location.js`'s `buildLocationPdf(placeName, ordered, imagesByPhotoId, qrDataUrl)`. `ordered` (`{ dated: [...], undated: [...] }`) is the exact same structure `orderPhotos()` builds for the HTML timeline — extracted into its own function specifically so the PDF and the page can never silently drift into showing photos in a different order from each other. The PDF walks the same list, one section per photo (image, bold caption, date/credit line, full History paragraph), with a single "Date unknown" heading before that group, same as the page.

## Display convention: thumbnail/map-sized vs the full photo page

Deliberate split, requested explicitly — don't blur it when adding fields:

- **Thumbnail/map-sized displays** (photo grid thumbnails, the map sidebar list, map popups) show only **Name, Date, Location** — compact, one or two lines. Grid thumbnails show this as a glass gradient-overlay caption (`.photo-thumb-caption` in `js/photos.js`/`css/style.css`, same visual language as the hero banner and category tiles); the map list/popups combine period+location into one subtitle line (`[item.period, item.location].filter(Boolean).join(" · ")`, in `js/map.js`).
- **The photo's own page** (`place.html?photo=ID`) is the one place that shows everything: Name, Date · Location, Category · Credit, written **History** (`.place-history`, only shown when `photo.history` is set), Ref, a small live preview map plus a link to the full map if located, the "Know more about this photo?" button, "View / Print PDF," and (if linked) the Story page's extra content and related photos.

Two optional fields on **both** photo entries and `data/map-pins.json` pins:
- `location` — free text, e.g. `"Garden Street"`. Not the same as `category` (Streets & Buildings etc.) — this is an actual place name, filled in by hand as it becomes known. Ordinary photos set it via the matching category's Photos collection in the admin; curated pins only via hand-editing `data/map-pins.json` directly now (no admin form for pins any more, see "Both 'Story pages' and 'Map pins' were removed" below).
- `history` — **photos only** (curated pins already have `description` serving the same role for their popup). A longer written paragraph, shown on the photo's page beneath the facts panel. Optional — most photos won't have one yet.

**Admin: `admin/index.html` + `admin/config.yml`** is [Sveltia CMS](https://sveltiacms.app/), backed by a direct **GitHub** OAuth connection (saves commit straight to `main`). `publish_mode: simple` — no draft/review step, matching the rest of the site's single-trusted-uploader approach; switch to `editorial_workflow` in `config.yml` if that ever needs to change (e.g. more admins added).

**Was Decap CMS + Git Gateway/Netlify Identity until this switch.** Reason: Event Pages needed genuine multi-file photo upload (see "Events" above), and Decap's media library doesn't reliably support selecting/uploading several images at once — confirmed both by direct testing (blocked on a real Mac) and by Decap's own open, unresolved GitHub issues asking the same question. Sveltia CMS is a from-scratch, actively-developed successor built specifically to be config-compatible with Decap (this migration needed **no changes to the photo/event data schema, folder layout, or categorisation** — only `admin/config.yml`'s `backend:` block and a handful of widget-name changes, covered below) and its `image` widget has a real, documented `multiple: true` option (a single field holding an array of paths, not the list-widget workaround tried first — see "Events" above for that history). Two real, deliberately-accepted trade-offs that came with switching:
- **Backend had to become GitHub OAuth, not Git Gateway** — Sveltia doesn't support Git Gateway and has no plans to. Netlify hosts the OAuth callback automatically once a GitHub OAuth App is registered (Homepage URL the site's own URL, Authorization callback URL `https://api.netlify.com/auth/done`) and its Client ID/Secret are entered into the site's own Netlify dashboard settings — a one-time, account-level setup step the site owner does directly in GitHub/Netlify, nothing in this repo. Login now goes through GitHub instead of Netlify Identity.
- **All custom admin JS was removed** (`CMS.registerWidget`/`registerPreviewTemplate`/`registerPreviewStyle`/`registerAdditionalLink`, previously in `admin/index.html`) — Sveltia's custom-field-type API (`registerFieldType`, aliased as `registerWidget` for Decap compatibility) is documented as "unimplemented — will be added soon," not actually shipped yet, and a config referencing an unregistered widget name fails validation for the *whole* admin, not just that field (confirmed the hard way with an unrelated list-widget config mistake earlier in this same project). Rather than risk that, every previously-`muted-*` field became a plain standard widget (`string`/`text`/`boolean`), and the custom photo-preview pane, custom preview stylesheet, and the (already broken — see below) Edit log page were all dropped rather than left half-working. Requested/accepted explicitly — the user cares about upload ease, not admin visual polish, and was clear about that trade-off.

**Photos: one collection per category, not one shared collection.** `admin/config.yml`'s `collections:` holds eleven near-identical Photos collections — the original six (`photos_streets`, `photos_people`, `photos_events`, `photos_nature`, `photos_aerial`, `photos_other`) plus five added later (`photos_churches`, `photos_groups`, `photos_industry`, `photos_schools`, `photos_sports` — Churches & Religious Buildings, Groups & Organisations, Industry, Schools, Sports) — labelled just "Streets & Buildings" etc in the sidebar (no "Photos —" prefix, removed at the user's request as unnecessary noise once every collection in the admin is a Photos collection anyway). Listed alphabetically among *every* collection in `config.yml` (not just these eleven — see "alphabeticalised" below), which also means **whichever one sorts first is what opens by default on login** (the CMS opens the first-listed collection) — currently Aerial, not "Streets & Buildings" as it originally was when that one was deliberately listed first for being the largest category; a straight tradeoff the user made explicitly, not an oversight. This is eleven collections rather than one `photos` collection with a Category dropdown because: **the image widget** has no way to route an upload into a folder based on the *value of another field in the same entry* — a field's `media_folder`/`public_folder` can only be a fixed path (optionally built from things like `{{slug}}`, but not from a sibling field's live value) — so there's no way to say "put this in `images/photos/streets/` if Category is set to Streets" within a single collection/field. Each collection instead has its own fixed `folder`/`media_folder`/`public_folder` pointing at its own category subfolder — that part of the reasoning still holds, and is why there still isn't one merged collection. `view_filters`/`view_groups` (the old quick-filter-by-category buttons) were dropped along with the earlier shared collection — no longer needed when each collection is already exactly one category.

The **`category` field itself**, though, no longer needs the same fixed-path constraint the image upload does — it's just a plain string in the saved JSON, not a folder path — so it's a real `select` widget now (options: all eleven categories, default matching the collection you're already in), not a `hidden` one. See "Recategorising a misfiled photo" below for what changing it actually does.

**Four of the eleven collections have `view_groups` back** — the ones expected to actually grow varied enough internally that one flat list becomes hard to browse (unlike e.g. Aerial or Sports, which don't really vary within themselves):
- `photos_streets`: `{ label: "Street", field: "location" }`.
- `photos_nature`, `photos_events` (the flat "Events (single photos)" collection, not Event Pages): both `{ label: "Location", field: "location" }` — same reasoning and same field as Streets.
- `photos_people`: `{ label: "Person", field: "personName" }` — grouped on a **new dedicated field**, `personName` ("Person / family name"), rather than the existing `caption`. Caption for a People photo is a full descriptive sentence ("Daisy Woodfield, Chalice Woodfield with cart at Grange Dairy," not just a name), so exact-match grouping on it would barely ever combine two photos of the same person — a much weaker fit than Location already was for Streets/Nature/Events. `personName` exists purely to be typed consistently for grouping (e.g. always "Owen Hartshorn"), same spirit as `placeId` — not shown anywhere on the site, just an organising field. Added to **all eleven** collections' `fields:` (not just `photos_people`), same reason `placeId`/`numberedPeople` are on all eleven: a photo recategorised away from People and later saved from another collection would otherwise silently lose whatever was typed into a field that collection doesn't list.

All four groupings share the same trade-off Streets already had: only as clean as the underlying field is worded consistently for the same person/place (e.g. always exactly "Melton Road," never sometimes with ", Thurmaston" tacked on) — inconsistent wording fragments into near-duplicate groups rather than erroring. Not added to the remaining seven collections — none of them are expected to have enough internal variety for a flat list to become hard to scan.

## Recategorising a misfiled photo — a dropdown, not a file move

A photo that's landed under the wrong category (filed into the wrong Drive subfolder originally, or just miscategorised by hand) is fixed by opening it in whichever collection it's currently sitting in and changing its **Category** dropdown — no dragging, no re-uploading, no deleting-and-recreating the entry. This works because the live site never reads which folder/collection a photo's file happens to sit in — every front-end script (`category.html`'s `?cat=` filter, the homepage category tiles, `js/map.js`'s pin colour) reads the `category` field stored inside that photo's own JSON, and `scripts/rebuild-photos-index.js` walks `data/photos/` recursively when building the aggregate rather than trusting each subfolder's name — so **the live site is already showing the corrected category the moment the CMS save lands**, before anything about the file's location changes.

The file's location does still get fixed too, just not synchronously in the same save — `scripts/rebuild-photos-index.js` (already run by `.github/workflows/rebuild-photos-index.yml` on every push touching `data/photos/**`, i.e. every Drive sync and every CMS save) now also compares each photo's `category` field against the subfolder it's actually sitting in, and physically relocates the file (`fs.renameSync`, same as `git mv`) into the matching category's subfolder whenever they disagree — checked against a fixed `KNOWN_CATEGORIES` set matching the eleven `photos_*` collections, so a typo'd or stale category value can never send a file somewhere nonsensical. That workflow already stages and commits `data/photos/` changes back to `main` regardless (it's what makes the `addedAt`/`ref` backfills, above, stick) — the relocate rides along on the exact same commit, no separate step. Practically: save the corrected Category, wait roughly a minute for that workflow to run, then that photo's entry shows up under the *right* collection's tab in the admin too, not just correctly on the live site. **The image file moves too, not just the JSON** — tried leaving it in place at first (reasoning: `src` is just a URL, doesn't need to live alongside the JSON), but that was wrong in practice: it meant a recategorised photo was the one photo on the whole site whose image folder didn't match its category, with no way for a non-technical editor to know why, since every *other* photo's image and category always do agree. Reported directly, from a real recategorised photo (Johnson's Bridge — category "Nature & Views," image still sitting under `images/photos/aerial/`) confusing exactly the person this whole feature exists for. Fixed: the image is now relocated alongside the JSON (parsed straight from the photo's own `src` field via `SRC_PATTERN`, not from the JSON's own folder, since that may have already moved earlier in the same rebuild pass) and `src` rewritten to match its new path. Both relocates independently skip (and log a warning) rather than overwrite, on the near-impossible chance a same-named file already exists at either destination — filenames start with a unique per-upload ID, so a real collision would mean something else has already gone wrong upstream.

**Adding a category is mechanical, not architectural** — done once already for Churches & Religious Buildings, Groups & Organisations, Industry, Schools and Sports (requested together, alphabetised on both ends). Every place a category slug/label appears, all kept in alphabetical order by label: a new `photos_<slug>` collection in `admin/config.yml` (copy an existing one, change the slug/label/folder paths, re-sort the whole `collections:` list — see the alphabetisation note below); a `CATEGORY_FOLDERS` entry in `automation/drive-photo-sync.gs.js` (so a matching Drive subfolder syncs automatically, same categorisation rule as above); a `MAP_CATEGORIES` entry in `js/map-categories.js` (label + a pin colour distinct enough from the others already in use); a `PHOTO_CATEGORIES` entry in `js/photos.js` (currently unused by any live code — kept accurate anyway rather than left to drift); a `CATEGORY_INFO` entry in `category.html`'s inline script (label + a one-line intro); a tile in `index.html`'s `#photo-filters` grid; and a chip in `map.html`'s `#map-filters` row (`All` always stays first, everything else alphabetical). Nothing in `js/photos.js`, `js/map.js`, `category.html`'s locked-category logic, or `setCategoryTileImages()` needed to change — all of that is already generic over whatever categories exist, reading from `MAP_CATEGORIES`/`[data-category]`/`?cat=` rather than a hardcoded list.

`data/photos/<id>.json` became **`data/photos/<category>/<id>.json`** to match — `scripts/rebuild-photos-index.js` walks `data/photos/` recursively (not just one flat level) to build the `data/photos.json` aggregate, so this didn't need to change how the *site* reads photos, only how they're filed. `automation/drive-photo-sync.gs.js` was updated the same way: `appendMetadataEntry`'s `dataPath` and `publishPhoto`'s `repoPath` (the actual image upload target) both now include `category` in the path (`images/photos/<category>/<filename>`, `data/photos/<category>/<id>.json>`) — `category` there is always already one of the six slugs (`CATEGORY_FOLDERS` maps Drive folder names to them), so no new mapping was needed, just threading the existing value into two more path strings. **`data/map-pins.json`'s curated pins** have their own `photoSrc` field (a hand-copied path to reuse an existing photo's image in the pin's popup, per its hint text) — these are **not** automatically updated by anything and had to be fixed by hand during this migration (two pins, "The Generous Briton" and "Manor Hotel," both pointed at the old flat path). If a curated pin's popup photo ever goes blank, check `photoSrc` against where that photo's `src` actually points now.

**No custom live preview any more** — `admin/index.html` used to register one (`CMS.registerPreviewTemplate` + `registerPreviewStyle`, a `PhotosPreview` component mirroring `place.html`'s real markup, registered once per category collection) so the preview pane looked like the live page while typing. Dropped in the Sveltia migration along with the muted widgets (see above) — same "custom registration API not confirmed/supported" reasoning, and not something the user asked to keep. The default generic Sveltia preview pane is what's shown now.

**Both "Story pages" and "Map pins" were removed from the admin at the user's request** — `admin/config.yml`'s `collections:` now holds only the six `photos_*` collections above. Removing them was purely subtractive on the admin side (`PagePreview`/`renderTextBlockPreview`/`renderInlinePreview`/`escapeHtmlPreview` and `MapPinsPreview` were all deleted from `admin/index.html` along with their collections — don't re-add just a preview without its collection, or vice versa) and **changes nothing about what the live site reads or renders**:
- `place.html`/`js/place.js` still reads `data/pages/<slug>.json` exactly as before for any photo whose `pageSlug` already points at one (e.g. `generous-briton`) — hand-editing that file (or a normal GitHub commit) is now the only way to add or change a Story page.
- `js/map.js` still reads `data/map-pins.json` exactly as before for curated pins — hand-editing that file directly is now the only way to add, edit, or remove a Map pin (name, coords, description, `pageSlug`, etc). Ordinary located photos still auto-generate their own map pin from the Photos collection with no change — that path never went through `map_pins` anyway.

**Two-way linking gotcha (historical, now fully moot)**: a photo's `pageSlug` and a story page's existence used to be two independent things set by hand in two different collections — nothing kept them in sync automatically, and creating a story page with a `photo` block pointing at photo X did **not** set photo X's own `pageSlug` back (this happened for real, for the Ian Lavendar photo/page). The Photos collection has never had a `pageSlug` field of its own (see "Every photo gets its own page" above), and now that `map_pins` has no admin form either, `pageSlug` can't be set through the admin at all any more — only by hand-editing JSON directly, which is inherently one edit at a time.

**`delete: true` on all six Photos collections** — lets an editor delete a photo entry from inside the admin (a "Delete entry" option appears when editing one), rather than needing a GitHub commit by hand. Turned on at the user's request; started as `false` (the conservative default from when the config was first scaffolded, never an explicit decision). **Known limitation, not fixable from `config.yml`:** the CMS's delete only removes the JSON entry (`data/photos/<category>/<id>.json`) — it does **not** also delete the uploaded image file (`images/photos/<category>/<file>.jpg`), so a deleted photo's image is silently orphaned in the repo (harmless — nothing links to it any more once its JSON entry is gone and `data/photos.json` is rebuilt — but it does sit there taking up space). If that ever needs cleaning up, it's a manual "find image files under `images/photos/` with no matching `data/photos/**/*.json` `src`" pass, not something the CMS can do for you.

**No more "muted" grey styling on fields** — every photo/event field (Caption, Date, Credit, Coordinates, Location, History, Consent, the Internal fields, etc.) is a plain, equally-weighted standard widget (`string`/`text`/`boolean`) now. Used to have a dimmed-grey custom styling (`muted-string`/`muted-text`/`muted-boolean`, `CMS.registerWidget`) for "usually fine as-is" fields, to visually recede them versus ones needing an active decision — removed entirely as part of the Sveltia migration (see "Was Decap CMS" above), a deliberate, explicit trade for reliable multi-photo upload, not an oversight. If this is ever missed enough to rebuild, note it'll need Sveltia's `registerFieldType` API to actually ship first (unimplemented as of this migration).

**Photo previews not showing in the admin — leading-slash bug, twice now.** Each Photo field's `media_folder`/`public_folder` (`/images/photos/<category>`, one per collection) start with a leading slash — but `automation/drive-photo-sync.gs.js` was writing every synced photo's `src` as `images/photos/<file>.jpg` **without** one. the CMS can't match that value against its configured media folder, so it fell back to using the raw string as a plain `<img src>` — which resolves fine on every top-level page (`index.html`, `place.html`, etc, all served from the site root) but breaks specifically in the admin, which lives one level down at `/admin/` (the relative path resolves to `/admin/images/photos/...`, which doesn't exist). Fixed both ends: `drive-photo-sync.gs.js`'s `appendMetadataEntry` now writes `src: "/images/photos/" + category + "/" + filename` (leading slash) for all future synced photos — note this is a *separate* string from the `repoPath` used for the actual GitHub upload call a few lines earlier, which must stay slash-less since it's a raw GitHub Contents API path, not a browser URL; don't accidentally unify those two. All 12 pre-existing photo files with the old slash-less `src` were migrated by hand to match (as part of the same pass that moved them into per-category folders — see above). If photo previews go blank in the admin again, check this first.

**Search in the Photos collections** — a search box is automatic on any folder collection in this CMS, no config needed, so each of the six category collections gets its own (searching only within that category — there's no single search box spanning all six any more, since there's no single collection to put it on). The old `view_filters`/`view_groups` (quick-filter-by-category buttons, grouping by category) were dropped when the shared `photos` collection was split up — pointless once each collection is already exactly one category.

**Back to site** — a plain `<a href="/index.html">` sitting right after `<body>` in `admin/index.html`, fixed bottom-right with a high `z-index` (first tried top-right — overlapped Decap's own live-preview toggle there, reported directly by the user and moved to bottom-left; later moved again to bottom-right, its current spot, at the user's request). Deliberately a plain anchor tag, not built through a CMS registration API — that was tried once already (`CMS.registerAdditionalLink`, under Decap) and turned out to be silently broken the whole time it was documented as working (`typeof CMS.registerAdditionalLink === "function"` evaluated false on the Decap build actually loaded). Lesson that still applies under Sveltia: don't trust a CMS extension-registration API is working from reading its docs alone — this project has no way to drive the real live admin, so anything routed through one needs the user to actually confirm it's visible before it's trusted.

**Edit log — removed entirely in the Sveltia migration.** Used to be a page listing recent GitHub commits (`admin/index.html`'s `EditLog` component), but it was already broken before this migration (built on the same dead `CMS.registerAdditionalLink` path as the paragraph above, so it never actually appeared in the admin) — not worth porting to Sveltia's different registration API for a feature nobody had actually seen working yet. If wanted again, it'd need building fresh against whatever Sveltia's real additional-pages API turns out to be, verified live before being documented as working.

**The Admin link on the homepage (`index.html`) opens in a new tab** (`target="_blank" rel="noopener"`, on both the header-nav and footer copies) — requested explicitly, so following it doesn't navigate the visitor's current tab away from the site they were just browsing. Other pages' Admin links were left as same-tab; only asked for the homepage.

**`index.html`'s Netlify Identity widget script + invite/reset-link redirect were removed in the Sveltia migration** — that `<script src="https://identity.netlify.com/v1/netlify-identity-widget.js">` and its `netlifyIdentity.on("login", ...)` handler only ever existed to catch an invite/password-reset email link landing on the homepage before bouncing into `/admin/`; with the backend now GitHub OAuth (see "Was Decap CMS" above), Netlify Identity issues no such links any more, so this was genuinely dead code, not just a stale comment — removed rather than left inert.

## Village Chronology: `chronology.html` + `js/chronology.js`

Requested to display a family-supplied Word document (~140 hand-written "year + what happened" entries, 1086–2011, Thurmaston Heritage Group's own chronology) as an interactive, downloadable, admin-editable timeline — reachable from a small homepage teaser card (`index.html`, between the Photo archive tiles and the Facebook callout), not the full ~130-entry list dumped directly onto the homepage itself. Putting the whole thing on the homepage was considered and rejected: this site was already deliberately redesigned once to stay photo-archive-first rather than several competing "look at this too" attractions stacked on the front page (see "Homepage: photo-archive-first" above) — a full chronology in-place would repeat exactly that mistake. A small teaser + dedicated page matches how Events already works.

- **`data/chronology.json`** (`{ "entries": [{ "year": "...", "text": "..." }, ...] }`) is a **single hand-curated file**, not one file per entry — deliberately the same shape the old `map_pins` collection used before it was removed from the admin (see `js/map.js`'s own comment on that file) rather than the per-entry-file-plus-rebuild-script pattern Photos/Event Pages use. A village chronology tops out at a few hundred entries at most — small enough to load and edit as one whole list in the admin, with no `scripts/rebuild-*.js` + GitHub Action needed at all: whatever the CMS saves *is* exactly the file the page reads, directly.
- **Seeded once** from the uploaded `.docx` via a one-off Python script (not committed — this was a manual, one-time import, not a repeatable pipeline): `python-docx` pulled every non-empty paragraph, a paragraph starting with a year-like token (`\d{3,4}`, optionally preceded by `c`/`c.` for "c1870"-style approximate years) started a new entry, anything else (no leading year — a wrapped continuation line in the original Word doc) was appended onto the previous entry's text. A repeated leading year token (the source had a couple of "1932 1932 Frederick..." typos) was stripped. Entries were then sorted by the first number found in their own Year field, since the source document itself wasn't strictly chronological throughout (e.g. a "1976" entry sitting between two 1870s entries, almost certainly a typo for "1876" in the original — left as-is rather than silently "corrected," since that's not this codebase's call to make; fix it by hand via the admin if it's confirmed wrong).
- **`admin/config.yml`'s `chronology` collection** — a `files:` single-file collection (`data/chronology.json`), holding one `list` field ("Timeline entries") with two sub-fields per entry: **Year** (free text on purpose, not a date/number widget — the source data mixes exact years, decades ("1850s"), approximate years ("c1870"), and ranges ("1848/9", "1914-18"), and forcing any of those into a stricter widget would either reject real entries or lose the "roughly this era" nuance) and **What happened**. Listed alphabetically right after `photos_aerial` (between Aerial and Events) — keeps "Aerial opens first by default on login" intact rather than shifting that default to Chronology by accident.
- **The admin's list of entries is `collapsed: true`** — with 130+ entries, every one expanded to its full Year/What-happened fields would mean a very long scroll just to reach the "Add" button, which (like every list widget in every Decap-compatible CMS, checked directly rather than assumed) always appends after the last item — there's no config option to move it to the top of the list instead. Collapsing every entry down to its one-line `summary` shortens that scroll considerably, even though it doesn't remove it entirely; click a row to expand it and edit that entry as normal.
- **`js/chronology.js` always re-sorts entries by year on load** (`parseYear` — first 3-4 digit number in the Year field, same "pull the first number out" approach `extractYear` in `js/main.js` uses for a photo's date) rather than trusting `data/chronology.json`'s own file order — the admin's own hint text says entries can be added anywhere in the list ("order doesn't matter for saving"), so the page has to be the one place true chronological order is guaranteed.
- **Grouped into six coarse era bands** (Before 1700 / 1700s / 1800s / 1900–1949 / 1950–1999 / 2000 onward, plus a "Date unknown" catch-all if a future entry's Year field has no parseable number) — both as `<h2>` section headings down the timeline and as quick-jump pill buttons above it (reusing `.map-filters`' button styling). Purely a browsing aid computed fresh from each entry's Year on every load, not stored data.
- **A plain client-side text filter** (`#chronology-search-input`, filtering the in-memory `allEntries` array against year+text combined) — not the shared site-wide search overlay (`js/main.js`'s `wireSearchBox`), since that searches *across* pages/photos, while this is "find something within this one long list," the same distinction `category.html`'s dropped custom filter vs. its current shared-search-box already drew (see "category.html's search box" above). Clicking an era button clears this filter first, so jumping to a section can't land on something a search has just filtered away.
- **Visually, a `.chronology-entry` is `.location-entry`'s left-rail timeline look minus the photo column** — a chronology entry is text-only, so there's no thumbnail/media slot to lay out, just a bold Year label and the description alongside it (stacked on mobile).
- **Downloadable as a PDF** — same shared `js/pdf-helpers.js` "open in a new tab" pipeline every other PDF on this site uses (`openPdfInViewer`, `ensureSpace`/`addPdfHeading`/`addPdfParagraph`, the QR-code-to-`chronology.html` footer). Simpler than `location.html`'s PDF: no images to preload first, since every entry here is text-only.
- **Linked to from a photo's own page and an Event Page, by year** — requested explicitly ("how can we link entries on the site to the chronology"). `js/place.js`'s `renderChronologyBanner` and `js/event.js`'s equivalent both call the shared `extractYear(date)` (same year-extraction `js/main.js` uses everywhere else, including its "Added `<Month> <Year>`" placeholder exclusion, so a photo with no real date yet doesn't link to a made-up year) and, if it returns one, show a "See everything from `<year>` →" banner — reusing `.place-location-banner`'s exact styling (an eye-catching box, not a plain text link, for the same reason that class exists: a plain link in this spot went unnoticed before) — linking to `year.html?year=<year>` (see "Year pages" below).
- **Every chronology entry is individually in the shared site search too** ("Add years into the search") — `js/main.js`'s `initSearch()` consumes `CHRONOLOGY_DATA_PROMISE` (a module-level promise, fetched once — see "Glass/Apple-style redesign" below for why it's shared rather than each consumer fetching its own copy) and adds one search entry per chronology row: title is the entry's own Year, excerpt is its text, linking to `year.html?year=X` when its `sortYear` is set. Typing a year ("1945") or a keyword from an entry's text ("Domesday") into the header search or homepage search box now surfaces the specific chronology row, not just the one generic "Village Chronology" page link that was already in `SITE_SEARCH_INDEX`. **Real bug caught and fixed while building this**: with two independent async sources (photos, chronology) each naively doing `searchIndex = SITE_SEARCH_INDEX.concat(ownResults)`, whichever fetch resolved *last* would silently wipe out the other's contribution — fixed by keeping `photoEntries`/`chronologyEntries` in their own variables and rebuilding the combined `searchIndex` from all three every time either one resolves, instead of each callback rebuilding "static + just its own results" from scratch.
- **Superseded, not documented in detail here any more**: an earlier version of this feature (i) made `chronology.html?year=1929` scroll to and highlight the matching entry in place (`applyYearParam`, `.chronology-entry-highlight`), and (ii) auto-computed a "Related: `<link>`, `<link>`" line under any entry whose year matched a photo/event's own date (`.chronology-related`). Both were removed once "Year pages" (below) shipped — a dedicated page per year is strictly more useful than either a highlighted row or an inline related-links list, so there was no reason to keep maintaining both. An old bookmark to `chronology.html?year=X` now just lands at the top of the page — same accepted-regression pattern as the old `index.html#map` anchor (see "Homepage: photo-archive-first" above).

## Shared memories: `data/memories.json`, admin-editable

The homepage's "Shared memories" section (three starter placeholders — "The old Melton Road shops," etc.) used to be hardcoded HTML `.card` blocks directly in `index.html`, not editable without touching code. Requested to make these editable via the admin.

- **`data/memories.json`** (`{ "entries": [{ "meta": "...", "title": "...", "text": "..." }, ...] }`) — a single hand-curated file, same shape/reasoning as `data/chronology.json`: this list is expected to stay small and admin-curated (memories get reviewed and added one at a time, not bulk-imported), so a `files:` single-file CMS collection with a `list` field is enough — no per-entry file + rebuild script needed, unlike Events/Graves.
- **`admin/config.yml`'s `memories` collection** — Label (defaults to "Shared memory," so a freshly-added entry doesn't need it typed every time — the three seeded placeholders keep "Placeholder story" instead), Title, Memory (the body text), and an optional Photo. A memory's photo (`entry.photo`) renders as `.card-photo` — bled out to the card's own edges via a negative margin equal to the card's own padding (`.card` got `overflow: hidden` to clip the image's square corners to the card's rounded ones), rather than sitting inset like a normal `<img>`, so a memory with a photo reads as a photo card and one without still reads as a plain text card — not a half-empty image slot.
- **`index.html`'s three hardcoded `.card` blocks were replaced with an empty `#shared-memories-grid` container** + a not-found paragraph (shown only if `entries` is empty), rendered by the new `js/memories.js` (fetch, map to `.card` markup via the shared `escapeHtml`/`formatMultilineText` helpers, same pattern as `js/events.js`'s tile rendering). `data/memories.json` was seeded with the exact same three placeholders' text so nothing visually changed by shipping this — **except** the first placeholder's inline "`Share yours` to fill it in" link, dropped for consistency with the other two plain-text entries (the page's own "Share your memory" form sits right below this section anyway, so the extra inline CTA was redundant) — a plain `text` widget doesn't support embedded markup the way Story-page blocks do (`js/place.js`'s `renderInline`), and adding that just for one seeded sentence wasn't worth it.

## Year pages: `year.html?year=X` — everything from one year, pick-your-own PDF

Requested to replace the chronology's inline "Related:" links with something more useful: "if end user clicks on a year in the chronology a page appears with everything from that year," downloadable as a PDF where the visitor chooses what's actually included.

- **`js/year.js` fetches all three sources independently** (`data/chronology.json`, `PHOTOS_DATA_PROMISE`, `data/events.json` — the same three `js/chronology.js`'s old related-links feature used to fetch, before that was removed) and filters each to the one requested year: chronology entries via a locally-duplicated `parseChronologyYear` (same "first 3-4 digit number" logic as `js/chronology.js`'s own `parseYear` — two lines, not worth sharing across two pages that never load each other's script), photos/events via the shared `extractYear`. Not found (nothing in any of the three) shows the same `place-not-found`-styled empty state every other detail page uses.
- **Every matched item gets a checkbox, checked by default** (`.pick-checkbox`, `data-type="entry"|"event"|"photo"` + `data-id`) — chronology entries by array index (they have no stable id in the data), events/photos by their real `id`. "Select all"/"Select none" buttons just flip every checkbox's `.checked`; nothing about selection state is persisted anywhere, it's read fresh from the DOM the moment Download is clicked.
- **"Download selected as PDF" builds the document from whatever's checked at click time** — same shared `js/pdf-helpers.js` pipeline (`openPdfInViewer`, `ensureSpace`/`addPdfHeading`/`addPdfParagraph`, QR code linking back to `year.html?year=X`) every other PDF on the site uses. Preloads (`loadImageElement`) only the images actually needed: each selected photo's own image, plus each selected event's first photo as a small cover thumbnail (not its whole gallery — keeps the PDF from ballooning if someone selects several multi-photo events). Clicking Download with nothing ticked shows a plain `alert()` rather than silently producing an empty PDF.
- **Photos are a grid of `.photo-thumb`s (reusing the exact class `js/photos.js`/`js/events.js` already use), each with its checkbox absolutely positioned over its top-left corner** — a sibling of the `<a>`, not nested inside it, so a click on the checkbox never also triggers the thumbnail's own navigation to `place.html`. Chronology entries and events are plain checkbox+text rows (`.pick-item`) instead, since they don't need a grid.
- **Every existing "jump to a year" link across the site now points here instead of `chronology.html?year=X`** — `js/place.js`'s `renderChronologyBanner`, `js/event.js`'s copy of it, `js/main.js`'s `initHeroChronology` chips, and `initSearch`'s per-entry chronology search results. See "Superseded, not documented in detail here any more" under Village Chronology above for what this replaced.

## The pick-and-choose PDF pattern, generalised across the site

Asked directly to extend year.html's tick-a-box-then-download-a-PDF pattern everywhere on the site with more than one of something: photo categories, the Events landing page, a place's timeline, and the Cemetery directory. Rather than copy year.html's checkbox/PDF code four more times with the names changed, the reusable parts moved into shared code once, right after year.html shipped:

- **`.year-*` CSS classes were renamed to generic `.pick-*` ones** (`css/style.css`, "Pick-and-choose PDF pattern" block) — `.pick-toolbar`/`.pick-toolbar-actions` (the Select all/none + Download row), `.pick-list`/`.pick-item`/`.pick-item-body`/`.pick-item-title`/`.pick-item-meta`/`.pick-item-text` (checkbox + text rows — chronology entries, events, cemetery rows), `.pick-grid`/`.pick-photo-item` (checkbox overlaid on a photo tile — year/category/location photos). One set of classes shared by `year.html`, `category.html`, `events.html`, `location.html` and `cemetery.html`, not five near-identical ad hoc ones.
- **`js/pdf-helpers.js` gained the shared JS half**: `wireCheckboxSelectAll(selector, allBtn, noneBtn)` wires a page's Select all/none buttons; `checkedPickIds(selector)` reads whichever checkboxes are ticked *right now* into a `{id: true}` lookup (called fresh at the moment Download is clicked — there's no stored selection anywhere, same as year.html's original design); `addPdfImage`/`addPdfPhotoEntry`/`addPdfEventEntry` are the shared per-item PDF-block builders, used by every page that lists photos or Event Pages so the same photo/event never gets typeset two different ways depending which page's PDF it came from. `addPdfPhotoEntry` is a deliberate *union* of two slightly different photo-block versions that existed before this generalisation (`location.html`'s had credit/History but not Location text, `year.html`'s had Location text but not credit/History) — a strict improvement for both callers, not a lowest-common-denominator cut-down.
- **Each page still builds its own PDF layout and its own toolbar-visibility rule** — those genuinely differ enough not to share:
  - **`category.html`** (`js/photos.js`): photos are now ordered **oldest-first by real date** (`orderPhotosChronologically`), not newest-uploaded-first — requested explicitly ("chronologically"), a deliberate change from the previous "most recently added" convention. The picker toolbar only appears once *every* matching photo is actually rendered with a checkbox — while the existing `PREVIEW_COUNT` cap is still showing just the first 8, showing "Select all" would silently only ever select those 8, which reads as a bug ("I picked select-all, why is my PDF missing photos?"), not the deliberate space-saving the cap is everywhere else on this page. It only reveals itself once "Show all" is clicked (or the category was never capped to begin with).
  - **`events.html`** (`js/events.js`): Event Pages tiles get the same oldest-first-by-date reordering, each wrapped in a `.pick-photo-item` with a checkbox; the PDF combines each selected event's cover photo + name + date + description via the shared `addPdfEventEntry`.
  - **`location.html`** (`js/location.js`): already had one combined PDF of every photo at a place (unaffected — this is the "more than one entry" case that existed before this pattern had a name); this pass just added a checkbox to each `.location-entry` (wrapped in a `.pick-photo-item` sized to match the existing 180px thumbnail column) and Select all/none, which only appear when there's more than one photo. The PDF filters to whatever's checked using the newly-shared `addPdfPhotoEntry` instead of its own now-deleted `addLocationPdfEntry`.
  - **`cemetery.html`** (`js/cemetery.js`): kept its existing **alphabetical-by-name** order rather than switching to chronological — a directory for finding a specific person by name is more usable sorted that way than by death year, and the user's "chronologically" framing was about browsing a *feed*, not looking someone up. Its own PDF entry builder (`addGravePdfEntry`, not shared — no other page has graves) includes name, number/dates, what3words address, inscription and notes, plus the headstone photo if one's been added.

## Cemetery: `cemetery.html` (directory) + `grave.html?grave=<id>` (one headstone)

Requested to make the village cemetery searchable: headstones are numbered on the ground, and each one's exact spot can be recorded as a [what3words](https://what3words.com) address — so a visitor can search a name and get back the grave number plus exactly where to walk.

- **Scope decision made up front, worth knowing if this ever gets revisited**: the user has overhead drone photos of the cemetery and floated plotting numbered, clickable pins directly on them. Deliberately **not built that way** — the photos aren't georeferenced (no real-world GPS for their corners/edges), and a what3words link already opens What3Words' own live map centred exactly on the 3m square, so a second, hand-plotted pin map would be duplicate effort for very little extra benefit, plus it would need every grave's pixel position entered by hand in the CMS (fiddly, easy to get wrong, no built-in Decap/Sveltia widget for "click a photo to set a point"). Went with a plain searchable directory instead — the drone photo is just an optional overview image at the top of `cemetery.html`, not an interactive map. If real georeferencing ever becomes available (a proper drone-mapping export with known corner coordinates), a Leaflet `ImageOverlay` pin map becomes viable and would slot in without touching the data model below.
- **`data/graves/<id>.json`, one file per headstone** (`admin/config.yml`'s `graves` collection, folder `data/graves`) — same per-entry-file-plus-rebuild-script shape as Event Pages, not Chronology's single hand-curated file, since the eventual number of headstones is unknown and could be large, and each is edited independently by whoever's doing the survey (unlike the chronology, which was one bulk historical import). Fields: **Name(s) on the headstone** (free text, not split into separate fields — a shared/family headstone can carry more than one name, e.g. "John Smith & Mary Smith," and either name is individually searchable since matching is a plain substring check against the whole string), **Grave number**, **Dates**, **what3words address** (plain string, e.g. `index.home.raft` — see below for why this is never computed), **Inscription**, **Notes**, and an optional headstone **Photo**.
- **What3words is stored as plain admin-entered text, never called as a live API** — deliberate, matching how photo GPS coordinates already work on this site (paste the answer once, don't compute it on every page load). A grave's location never changes, so there's no ongoing sync problem, and it avoids needing a What3Words API key/backend at all for what would otherwise be a pure lookup. `js/grave.js` builds the outbound link itself (`https://what3words.com/<words>`, stripping any leading `///` someone might paste from the What3Words app) rather than embedding their map widget.
- **`scripts/rebuild-cemetery-index.js`** builds `data/cemetery.json` from `data/graves/*.json` — same shape of job as `rebuild-events-index.js` (id from filename, backfill+persist `addedAt` once) but **sorted alphabetically by name**, not newest-first — this is a directory people browse to find someone, not a feed of what was added most recently. Wired into the same `.github/workflows/rebuild-photos-index.yml` (triggers on `data/graves/**` too), with the same "directory might not exist yet" guard on `git add data/graves/` that Events already needed.
- **`admin/config.yml`'s separate `cemetery_overview` collection** (`files:`, single file `data/cemetery-overview.json`, one optional image + caption) is what puts the drone photo at the top of `cemetery.html` — kept as its own tiny single-file collection (same pattern as Chronology's `files:` collection) rather than a field embedded anywhere else, since it's one photo for the whole page, not one per grave.
- **`cemetery.html` / `js/cemetery.js`** — the overview photo (hidden entirely if none has been uploaded yet), a "Search for a name" box wired through the exact same shared `wireSearchBox`/whole-site index as every other search box on the site (typing a name here can also surface a matching photo or event — a feature, not noise, same reasoning already established for `category.html`'s own search box), and a plain alphabetical `<ul>` directory of every grave underneath for browsing without needing to already know a name.
- **`grave.html` / `js/grave.js`** — mirrors `event.html`/`js/event.js`'s structure (heading/crumb/subheading, not-found state, the shared `.place-zoom-overlay` + `vendor/panzoom` for the headstone photo) rather than `place.html`'s heavier one (no mini-map, no PDF export, no "Know more" popup — none of those were asked for here and there's no GPS data to put on a mini-map anyway). The what3words address is shown via a prominent `.place-location-banner`-styled link ("Find this grave: `///index.home.raft` — open in what3words →"), the same eye-catching-banner class already used for the Chronology year-nudges on photo/event pages, opening in a new tab.
- **Every grave is individually in the shared site search** — `js/main.js`'s `CEMETERY_DATA_PROMISE` (fetched once, shared between `initSearch()` and `js/cemetery.js`'s own directory listing, same sharing pattern as `CHRONOLOGY_DATA_PROMISE`) feeds one search entry per grave: title is the name, excerpt is grave number + dates, linking straight to `grave.html?grave=<id>`. This is the actual point of the feature — type a name into any search box on the site (header overlay, homepage, category page, or the cemetery page's own box) and land straight on that grave's number and what3words location.
- **Nav/footer**: every page's main nav and footer "Explore" list got a "Cemetery" link alongside Photo Archive/Interactive Map/Village Chronology; `SITE_SEARCH_INDEX` got a static "Cemetery" page entry too, for parity with the other landing pages.
- **A sensitivity note, not a built feature**: real names and dates of the deceased are a step more sensitive than old street photos — flagged to the user when this was scoped, no gating (e.g. a "recent burials" cutoff) was requested or built. If that's ever wanted, it'd be a new boolean field on the `graves` collection plus a filter in `rebuild-cemetery-index.js`/`js/cemetery.js`, not a structural change.

## Glass/Apple-style visual redesign

Requested explicitly ("more modern, perhaps more glass like akin to apple styling") — keeping the existing green/gold/cream palette (a *treatment* change, not a re-palette), keeping both search boxes working exactly as before, keeping the hero's info + village photo, and weaving the Village Chronology into the hero itself rather than leaving it as a separate callout further down the homepage ("That will mean adjusting things to suit" — explicit permission to restructure the hero's layout to fit it in).

**Scope was deliberately split, not a single full-site pass**: sitewide, mechanical, low-risk token/selector fixes (safe everywhere, no layout math changes) plus one genuinely new piece of layout — the homepage hero. Retrofitting a full type-scale/spacing-scale onto every one-off value across all 10 pages, consolidating the ad hoc breakpoint set, and a `prefers-color-scheme` dark mode were all considered and explicitly deferred — bundling a full site-wide rescale with the hero rebuild in one pass, with no test suite and no build step, would have been a much bigger surface to visually re-verify by hand than this ask warranted. `admin/` (Sveltia CMS) was untouched throughout.

## Backup: GitHub → Drive, one-way, editorial data only

`backupToDrive()` in `automation/drive-photo-sync.gs.js` is a separate function (own daily trigger, not part of `syncPhotos`) that reads the live `data/photos.json`, `data/map-pins.json`, and every `data/pages/*.json` from GitHub and writes them into a Google Sheet ("Memories of Thurmaston — site backup") inside the same Drive folder, overwriting it each run. Requested explicitly as *just* a safety net, not a working copy — don't build anything that reads from or writes back into that sheet; it's one-way, GitHub is still the single source of truth. The photos themselves don't need backing up (they started in Drive); this exists because the editorial layer on top — cleaned captions, `location`, `history`, map pin descriptions, story page text — only lives on GitHub otherwise.

**One deliberate exception to "one-way":** after each run, `writeBackupStatus()` commits a small `data/backup-status.json` (`{ lastBackedUp, sheetUrl }`) back to GitHub — asked directly ("can I have a 'last backed up' within the admin section"). This is the *only* thing this feature writes back into GitHub; it still doesn't read from or restore anything out of the Sheet. `admin/index.html` shows it as a small fixed badge (bottom-right, mirroring the existing "Back to site" link's "plain DOM element floated above whatever Sveltia mounts" trick, bottom-left — swapped from the original bottom-left/bottom-right at the user's request, no other change) — a plain `fetch("../data/backup-status.json")`, no Drive/Sheets API access needed client-side. Shows "No backup recorded yet" if the file is missing (before the first scheduled run since this shipped) or unreachable, never a broken-looking blank badge.

**If the badge has shown "No backup recorded yet" for a while, the likely cause isn't a bug — it's that `backupToDrive`'s own trigger was never actually added.** `syncPhotos` (photo import) and `backupToDrive` (this badge) are two independent Apps Script triggers; pasting this file's code into the Apps Script project only makes both functions *available*, each one still needs its own entry added under Triggers → Add Trigger in the Apps Script editor itself (see the "BACKUP TO GOOGLE DRIVE" setup comment near the top of this file). `data/backup-status.json` not existing in the repo at all (rather than existing with an old date) is the tell — that file is only ever written by a successful `backupToDrive()` run, so its total absence means one has never completed, which points at the trigger never having been added rather than at anything erroring mid-run.

## Bug, fixed: `"url('" + src + "')"` silently breaks for any photo filename containing an apostrophe

Reported as "nature and views isn't showing on the tile on the home page." The nature category's newest photo was a real archive photo whose filename is `114 Johnson's Bridge and 'the plank'.jpg` — both an apostrophe and a single-quote-wrapped phrase. Three places built a CSS `background-image` value by hand-concatenating `"url('" + src + "')"`: `js/photos.js`'s `setCategoryTileImages()` (homepage category tiles), `js/main.js`'s `initHero()` (hero photo rotation), and `js/events.js`'s `renderTile()` (Events landing page tiles, built into an HTML string rather than a direct `.style` assignment). Any filename containing an apostrophe closes the CSS string early, so the browser rejects the whole `background-image` value as invalid — and `el.style.backgroundImage = "<invalid>"` is a silent no-op per the CSSOM spec: no exception, no console error, no failed network request, the assignment just doesn't apply. This is why it took real debugging to find (see the temporary-`console.log`-in-the-live-file method, standard for this class of bug on this project) rather than showing up as an obvious error — the tile just stayed blank.

**Fixed everywhere with `JSON.stringify(src)` instead of `"'" + src + "'"`** — it produces a correctly double-quoted, properly-escaped CSS string regardless of what punctuation the filename contains. `js/photos.js` and `js/main.js` do this as a direct `.style.backgroundImage` assignment. `js/events.js` needed a different mechanism since its tile markup is built as one big HTML string: the cover photo's `src` is written into a `data-cover="…"` attribute (HTML-entity-escaped, same as everywhere else in that string) and then, in a loop that runs *after* `tilesEl.innerHTML = …` inserts the markup, each tile's `.photo-filter-photo` span gets `style.backgroundImage = "url(" + JSON.stringify(cover) + ")"` set from `dataset.cover`. HTML-escaping the old inline `style="background-image:url('…')"` attribute value wasn't a fix for this — once the browser decodes the HTML entities back out, the resulting CSS text still has a raw apostrophe breaking the same `url('...')` syntax; this needed the `data-cover` + post-render `JSON.stringify` split instead, a genuinely different escaping context (HTML attribute vs. CSS string value).

**If you ever add a fourth place that sets a `background-image` (or any other CSS value) from a filename/caption/user-editable string, use `JSON.stringify(value)` inside `url(...)`, never `"'" + value + "'"`.** This bug went unnoticed for as long as it did specifically because it's silent — no error anywhere — so a real archive photo with an apostrophe in its name is the only thing that catches it.

## Bug, fixed: the "Rebuild photos index" GitHub Action was silently failing on every run since 2026-07-26

Reported as "photos aren't uploading." They were — the CMS side worked fine on every attempt, creating/updating the right `data/photos/<id>.json` file each time. What was actually broken was `.github/workflows/rebuild-photos-index.yml`, the workflow that regenerates `data/photos.json` (the aggregate the live site's `js/photos.js` actually fetches — see "Photos: one file per photo, plus a generated aggregate") and commits it back. It had been failing on *every single run* from 2026-07-26 07:15 onward, so `data/photos.json` on `main` was frozen at whatever it was as of the last success (06:55 that day) — anything uploaded after that point had a perfectly good `data/photos/<id>.json` file sitting in the repo, it just never made it into the aggregate the site displays. Confirmed via `mcp__github__actions_list`/`get_job_logs` on the repo's own Actions history, not guessed at.

**Root cause**: `rebuild-photos-index.js` can physically relocate a photo's actual image file (not just its JSON record) — moving it under `images/photos/<category>/` whenever the `category` field doesn't match the folder it's sitting in (see "Categorisation rule" above; this is the mechanism, not a new one). The workflow's "Commit and push if changed" step only ever `git add`ed the `data/` paths — `data/photos.json data/photos/ data/events.json data/cemetery.json` (plus `data/events/`/`data/graves/` conditionally) — never `images/`. So the moment any relocation happened, the commit captured the *data* index update fine, but the actually-moved image file (deleted from its old path, untracked at its new one) was left unstaged in the working tree. `git pull --rebase origin main` then failed with "You have unstaged changes. Please commit or stash them." on every one of its 5 retries, and — because the very same mis-filed images were still sitting there unrelocated on `main` for the next run to trip over — every subsequent run failed at the exact same step, indefinitely, until someone looked at the Actions log directly (nothing about this surfaces anywhere a non-technical site owner would see it; the CMS itself reports success because it is a separate, working commit).

**Fixed** by adding `images/photos/` to that `git add` line. Also fixed the immediate backlog by hand: ran `rebuild-photos-index.js`/`rebuild-events-index.js`/`rebuild-cemetery-index.js` locally once (reproduced the identical 4 relocations the CI logs showed — 3 Johnson's-Bridge-area nature photos and one sports photo that had been uploaded into the wrong category folder), then committed and pushed the resulting `data/photos.json` (23 → 27 photos) and the relocated image files directly, rather than waiting on the next CMS upload to re-trigger the (now-fixed) workflow.

**If this ever recurs, check the Actions tab (or `mcp__github__actions_list` → `list_workflow_runs` → `get_job_logs` with `failed_only:true`) before assuming the CMS itself is broken** — a photo that "isn't uploading" from the site owner's point of view can just as easily mean the aggregate rebuild is silently failing downstream of a perfectly successful CMS commit, and the two are diagnosed completely differently.
